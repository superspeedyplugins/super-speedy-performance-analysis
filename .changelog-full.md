# Super Speedy Performance Analysis - full engineering changelog

Long-form companion to the customer-facing changelog in `readme.txt`. Newest first.

## 0.11.4 (7th August 2026)

### Excimer installs via the distro package, targeted at the site's PHP version

> * The excimer install steps now use your distribution's package (`php8.3-excimer` style
>   on Debian and Ubuntu, Remi's `php-pecl-excimer` on RHEL and Fedora,
>   `php83-pecl-excimer` on Alpine), named for the exact PHP version the site runs so
>   servers carrying more than one PHP enable it for the right one; pecl remains only
>   where no package exists, as upstream no longer publishes excimer releases there.

**The trigger.** Upstream's page (mediawiki.org/wiki/Excimer) now states PECL is
deprecated and new releases will not be published there - and PECL itself carries a
platform-wide deprecation banner pointing at PIE. Excimer 1.2.6 (April 2026) is the last
version on PECL. Verified availability at the time of writing: Debian trixie 1.2.3, Ubuntu
noble 1.1.1 / jammy 1.0.2 (stock), deb.sury.org 1.2.6 built for every PHP 7.1-8.5, Remi
`php-pecl-excimer`, Alpine `php8X-pecl-excimer` 1.2.6. Our profiler only uses the base
`ExcimerProfiler` API, present since 1.0, so any of those versions works.

**Why the package beats pecl anyway.** A pecl-compiled `.so` is built against one PHP API
version; the next PHP upgrade moves the extension dir and the profiler silently vanishes
from the site. The distro package rebuilds with PHP through the package manager, ships its
own ini and enables itself - so the packaged path is three steps (install, restart,
verify) with no build tools and no hand-written ini, where a leftover manual
`20-excimer.ini` would collide with the package's identically-named symlink.

**The versioned-name trap, hit live.** Migrating the production superspeedyplugins box
(noble + sury, site on PHP 8.3 FPM, 8.5 also installed) showed that sury's unversioned
`php-excimer` is a metapackage that installs for the repo's *newest* PHP - it enabled
excimer for 8.5 and left the site's 8.3 without it. The generated command therefore leads
with `php<major.minor>-excimer` derived from the PHP actually serving the site, with an
unversioned fallback commented for stock Debian/Ubuntu, which only carry `php-excimer`.
The verify step names the versioned CLI binary (`php8.3 -m`, `php83 -m` on Alpine) for the
same reason, and points at the Tools tab Re-check as the authoritative test since it asks
the exact PHP process serving the site.

### tideways_xhprof was never on PECL

> * The `tideways_xhprof` install steps now build the extension from its source
>   repository, `github.com/tideways/php-xhprof-extension`.

Found while in the file: the generated step said `sudo pecl install tideways_xhprof`, but
no such PECL package has ever existed (pecl.php.net/package/tideways_xhprof is a 404 -
PECL's `xhprof` is the original extension, a different API). The command would have failed
on every system. It is now a source build with the same shape as SPX, and the build-tools
step for source builds asks for git plus a compiler instead of php-pear. `host_message()`
was updated in the same pass: the ask-your-host ticket now gives the distro-package
commands for excimer (naming the site's PHP version so a multi-PHP host installs for the
right one) and the source-build commands for tideways_xhprof and SPX.

`15-tools.php` pins all of it: packaged distros get exactly 3 steps with no `pecl
install` and no hand-written ini, apt commands must carry the running PHP's version, the
verify step must not use plain `php -m` on apt/Alpine, and tideways_xhprof must reference
its real source repo. Suite run in the Docker env (WP 7.0.2, Alpine 3.24, so the apk path
was exercised live): 0 failures.

## 0.11.3 (7th August 2026)

### Deterministic misbehaviour signatures

> * New deterministic misbehaviour signatures in the checkout analysis ...

The three patterns the live run exposed are general - any HPOS store running nginx-helper
(every GridPane site ships it preconfigured) exhibits the first, and the others are common -
so they are now recognised mechanically. `SSPA_Analysis_Engine::checkout_http_signatures()`
evaluates closed predicates over the captured outbound calls:

- **order_page_purge**: a blocking call to this site whose `?p=` value is one of the run's
  own order ids (now recorded in the run notes precisely for this). Deterministic because
  the placeholder post id IS the order id, on both HPOS and legacy storage. Always critical:
  purging an order's "page" is wrong on every store.
- **amp_purge_missing**: a blocking self-call whose path ends `/amp/` while no AMP plugin is
  active (`AMP__VERSION` / `AMPFORWP_VERSION` / `amp_is_enabled`).
- **self_fetch_failed**: a blocking self-call that errored at or beyond
  `checkout_self_fetch_ms` (feed threshold, default 1000ms).

Design decision, deliberately recorded: **predicates are code, copy and thresholds are
data**. The recommendations and thresholds ride the existing signed superspeedy.org rules
feed (bundled snapshot as offline fallback), so wording improves and thresholds tune without
a release; the matching logic stays in PHP because three signatures do not justify a
predicate DSL. If the catalogue grows past a dozen, the intended evolution is a
closed-vocabulary condition schema in the feed (`fact`/`op`/`value` triples over the same
call fields) evaluated by a small interpreter - still fully deterministic, never an LLM.
Matching is by behaviour, never plugin name, so hosting-company forks attribute correctly
via the component map.

To make the `?p=` check possible the capture now keeps VALUES for a whitelist of routing
keys (`p`, `page_id`, `post_type`, `attachment_id`, `paged`) that cannot carry secrets;
every other query key remains key-only.

Case 19's fixture now mimics all three behaviours (an `?p=<order id>` fetch, an `/amp/`
fetch, and a 1.4s endpoint hit with a 1s timeout) and asserts each signature fires and is
attributed to the fixture plugin: 99 assertions.

The companion fix lives outside this plugin: `scalability-pro/.docs/2026-08-07-checkout-
purge-shield.md` designs the spro filters that neutralise all three behaviours reversibly
(unhook nginx-helper's order-note comment purges, short-circuit self-fetches of
non-viewable permalinks and phantom `/amp/` URLs at `pre_http_request`, make `/purge/`
traffic non-blocking).

## 0.11.2 (7th August 2026)

Driven by the first checkout-flow run against the real superspeedyplugins.com store, which
surfaced one measurement-contamination bug, one boundary-placement bug, one cleanup gap, one
counting bug and two display gaps. The diagnosis is worth recording because the raw numbers
looked wrong and were in fact three-quarters right.

### The run that prompted it

The live run reported a 28.3s customer wait with nginx-helper attributed 25.77s. Reconciling
the outbound-call list against the roll-up showed the attribution was arithmetically sound -
nginx-helper really did spend that wall time blocked in its own HTTP calls - but ~6.2s of it
belonged to the harness's delete step and pre-flight, not the purchase. Pulling the stored
capture off the live site (the per-call `caller` field, which the panel did not yet display)
plus the live `rt_wp_nginx_helper_options` row and the nginx-helper source gave the full
chain:

- Every order status change and order note makes nginx-helper purge the "post" behind the
  order. With HPOS that post is a `shop_order_placehold` draft whose permalink is
  `/?p=<id>` - and the capture dropped query strings from display, so those showed as
  fetches of the bare homepage. Each one hung ~4.5-4.7s and died as
  `error:http_request_failed` (WP's default 5s timeout), three times inside place-order.
- `purge_amp_urls` fetches `<url>/amp/` RAW - no `/purge/` prefix - so on a store with no
  AMP pages each "purge" renders a full 404 page (~750ms each).
- The author-archive purges (`/author/sspa-test/`) exist because guest checkout is disabled
  on that store, so the Store API auto-created a customer account for the purchase - which
  the 0.11.1 cleanup did not remove. Real residue in a real user table.
- Mailgun's HTTP mode replaces the pluggable `wp_mail()` and never fires
  `wp_mail_succeeded`/`wp_mail_failed`, so three ~540ms sends were recorded as
  "1 message in 0ms".

### Harness contamination

> * Fixed the checkout flow's own pre-flight and cleanup steps leaking into the component
>   roll-up, the outbound-call list and the mail totals, which could overstate a
>   cache-purge plugin's cost by a quarter.

`waterfall()` collected the Excimer roll-up, the HTTP calls and the mail counts BEFORE the
harness-step exclusion `continue`. The waterfall totals and the findings engine were already
clean; the three panels underneath were not. Collection now happens only for customer-facing
steps, and case 19 plants a fixture that makes an HTTP call during order CANCELLATION -
i.e. during the delete step - and asserts it appears nowhere.

### The payment boundary was on the wrong side of the cascade

> * The payment boundary is now stamped at entry to `payment_complete()` ...

`WC_Order::payment_complete()` runs `woocommerce_pre_payment_complete`, then the status
transition and `save()` - which is where the order emails and everything hooked on the
transition fire - and only THEN the trailing `woocommerce_payment_complete` action we were
marking on. So the emails and purge cascade landed in the at-risk half. In sandbox mode the
gateway has returned successfully before `payment_complete()` is entered, so entry IS the
money-secured moment. The mark moved to `woocommerce_pre_payment_complete` with the trailing
action kept as an isset-guarded fallback. On the live numbers this flips the headline from
"22.8s at risk / 0.1s secured" to roughly "4s at risk / 19s confirmation-wait", which is the
honest story: the card would already be charged; the customer stares at a spinner while
purges time out.

### Auto-created customer accounts are now cleaned up

> * On stores that disallow guest checkout, the customer account WooCommerce creates for
>   the purchase is now deleted with the order ...

`woocommerce_created_customer` fires inside the flow's own place-order request; the account
is marked `_sspa_temp` and recorded in `sspa_flow_temp` immediately, deleted in the same
`finally` as the order, reported in the safety notes (`users_deleted`/`users_left`), and
swept by the hourly janitor (both from the option and by meta scan) if a crashed run
orphaned one. The pre-flight now discloses "this store creates an account for the purchase".
The type-aware `forget_temp_entries()` replaces the old id-only filter so a user entry can
never be dropped by an order-id collision.

### Finding spam, and the two display gaps

One `checkout_blocking_http` finding per component per step (count, total ms, failed count,
hosts, worst call with its caller) instead of one per call - the live run produced thirteen
near-identical criticals. The capture now keeps query-string KEYS (never values - they carry
secrets) so `/?p=123` is distinguishable from `/`, plus a short in-component `trace` of the
calling functions, and the panel prints method, keys and caller on every outbound call. The
`checkout_component_cost` recommendation also stops telling people to run checkout deep
analysis, which is not built yet (T13).

### Pluggable-wp_mail mailers are counted honestly

`mail_deliver_start` now flushes a still-pending send before starting the next one (sends
cannot interleave in PHP), so a mailer that replaces `wp_mail()` has every send counted with
an unknown duration rather than collapsing to one. The waterfall reports an `untimed` count
and the panel says "sent through a mail plugin's own transport - its time appears under
outbound calls" instead of the false "1 message in 0ms". Case 19 proves it with a fixture
that mimics Mailgun's override, guard and all.

Tests: case 19 grew from 54 to 96 assertions, including a forced-account purchase against a
guest-checkout-disabled store asserting zero user residue.

## 0.11.1 (7th August 2026)

### The classic shortcode checkout (T12)

> * The checkout flow now measures the classic shortcode checkout as well as the block
>   checkout, so a store using `[woocommerce_checkout]` no longer gets "Only the block
>   checkout is supported so far".

**Why it moved up the queue.** superspeedyplugins.com's own checkout page is
`[woocommerce_checkout]`, so 0.11.0 could not measure the store it was written on. Checked
before writing anything: the page content is the bare shortcode, and
`CartCheckoutUtils::is_checkout_block_default()` correctly returns false for it - the message
was accurate, not a detection bug.

**The steps** (doc C3): view product, `?wc-ajax=add_to_cart`, cart page,
`?wc-ajax=update_order_review`, checkout page, `?wc-ajax=checkout`, order received, delete.
Nine profile rows rather than the block path's twelve: there is no separate cart API call, no
separate rate-selection call and no draft order.

**The nonces, which are worse than the doc's A7 fact 8 says.** That fact records that
`wp_create_nonce()` binds to the current request's user and session token, so a nonce minted
inside the admin's AJAX request is bound to the admin. True, but incomplete: WooCommerce also
registers `nonce_user_logged_out` and rewrites the logged-out uid to the CART SESSION's
customer id for any action whose name starts with `woocommerce`
(`WC_Session_Handler::maybe_update_nonce_user_logged_out`). So:

- `woocommerce-process_checkout` is bound to a cart-session id that does not exist until
  add-to-cart has run,
- `update-order-review` does NOT start with `woocommerce`, so it stays on the plain
  logged-out uid.

`SSPA_Checkout_Flow::guest_nonce()` handles both: it strips the auth cookies, sets the current
user to 0, and filters `nonce_user_logged_out` at priority 100 - after WooCommerce's own at 10,
which would otherwise bind the nonce to THIS process's cart session. The session id itself is
read back out of the `wp_woocommerce_session_*` cookie that add-to-cart returned, so it is the
loopback visitor's own session rather than a guess.

Get this wrong and every classic checkout POST comes back "We were unable to process your
order, please try again", which reads like a broken store rather than a broken profiler. That
is exactly what the deliberate break produces, and case 19 asserts it does not happen.

**Shipping.** `wc_get_chosen_shipping_method_for_package()` defaults a rate into the session
while the order review renders, so validation passes even if nothing is posted. The flow still
parses the selected rate out of the returned fragment and posts it, because that is what the
browser does; an unparsed fragment is not fatal, it just leaves the default standing, exactly
as an untouched radio group would.

**Payment.** The same two `needs_payment` filters carry over unchanged.
`WC_Checkout::validate_checkout()` skips the gateway check at line 985 and
`process_checkout()` takes the `process_order_without_payment()` branch at line 1380, which
calls `payment_complete()` - so the post-payment cascade and the payment-boundary mark work
identically on both paths. Measured: 199.5ms of a 224.5ms place-order step was pre-capture.

### Cleanup notes were lost on every failure path

> * Fixed the run notes reporting "0 orders deleted" on a checkout flow that failed part way
>   through, when the order had in fact been deleted.

Found while building the classic path, and it affected the block path in 0.11.0 too. PHP
evaluates a `return` expression BEFORE running the enclosing `finally`, so every
`return $result;` inside `run()`'s try block handed back a copy of `$result` taken before
cleanup had recorded anything. The order really was deleted - the finally always ran - but the
run notes and the panel's safety report both said "0 orders deleted, 0 left" on any run that
did not reach the end. Case 19's residue assertions passed throughout because they count
actual orders rather than reading the notes.

Both paths are now separate methods (`run_block()` and `run_classic()`) called from a single
try/catch/finally in `run()`, so no early return can ever be inside the try again.

### Tests

Case 19 gains a classic section: the store is pointed at throwaway shortcode pages and put
back afterwards (the block pages are never edited), and the nine steps, the order status and
total, the payment boundary, real mail delivery and zero residue are all asserted again for
that path. The throwaway fixture products from the failure-path section are now deleted before
it runs - they are cheaper than the real target product, so leaving them published had the
classic run buy one of THEM, which made the stock assertion check a product the run never
touched.

Two assertions pin the nonce binding directly: the place-order nonce must differ both from an
unbound one and from one minted as the current admin, and the `update-order-review` nonce must
NOT differ, because its action name does not start with `woocommerce`. Broken on purpose by
removing the `nonce_user_logged_out` filter: the classic run fails with "We were unable to
process your order, please try again" and nine assertions fail, while every block assertion
still passes.

## 0.11.0 (7th August 2026)

Phase 1 of the checkout flow profiler, built from `.docs/2026-08-07-checkout-flow-profiling.md`
(tasks T1 to T11 plus the T14 test case). T12 (shortcode checkout), T13 (per-plugin checkout
isolation) and T15 (sandbox gateway adapters) are deliberately not in this release. Built and
tested against WordPress 7.0.2 and WooCommerce 11.0.0; the design doc was written against
WooCommerce 10.9.1 and every load-bearing fact in its A7 list was re-verified against 11.0.0
before any code depended on it.

### Measuring the purchase instead of the checkout page

> * New: "Analyse checkout flow" measures the server time your customer waits through at
>   every step of one real purchase, with every plugin on your site active, split at the
>   payment boundary so time that risks the sale is shown separately from time after the
>   money is in.

**The problem.** `SSPA_Catalogue::build()` profiles `wc-cart` and `wc-checkout` as static
GETs, which renders an EMPTY cart to a visitor with no session. On a block checkout the real
cost lives in POSTs a crawler never sends: `cart/add-item`, `cart/update-customer`,
`cart/select-shipping-rate` and `checkout`. Those two page figures were honest measurements of
something no customer experiences.

**What it does now.** `SSPA_Checkout_Flow::run()` drives twelve steps over loopback as one
routine - the cart item key, the shipping rate id, the order id and the confirmation URL are
each only knowable at run time, which is why this cannot be N independent queue jobs:
pre-flight, view product, add to cart, view cart, load cart data, enter address, select
shipping, view checkout, create draft order, place order, order received, delete order.

Every step is an ordinary profiled request, so the whole existing apparatus - SQL attribution,
HTTP capture, boot timing, the Excimer sampler - applies per step for free. The new transport
is `SSPA_Crawler::send_profiled()`, a sibling of `profiled_request()` that takes any method,
sends a JSON body, carries headers and cookies, and deliberately does NOT follow redirects: a
followed 3xx becomes a GET and would silently measure the wrong thing. `SSPA_Profile_Store`
stopped hard-coding `'method' => 'GET'`, so a POST step is no longer recorded as a page view.

**The payment boundary.** Slowness before the money is captured risks the sale; slowness after
it is a bad impression but the money is in. A single total hides that difference.
`SSPA_Checkout_Flow::mark_payment_complete()` stamps
`$GLOBALS['sspa_marks']['payment_complete']` from a `woocommerce_payment_complete` hook at
`PHP_INT_MIN`, the capture emits a generic `marks` section next to `boot` and `profile`, and
the panel splits the place-order row there. On a measured docker run that was 231ms at-risk
and 198ms post-capture inside one 429ms request. When the mark is absent the panel shows one
combined row and says the boundary could not be determined; it never guesses.

### Skipping the gateway without touching the totals

An earlier draft of the design used a 100% discount coupon to take the order total to zero,
because `WC_Order::needs_payment()` is `has_status(...) && get_total() > 0`. That mechanism is
real, and was rejected for three reasons recorded in the doc, the largest being that a
zero-value order makes integrations do LESS work: fraud screening, accounting sync, affiliate
commission and tax-commit integrations commonly short-circuit on zero-value orders, which
under-measures the exact thing the feature exists to measure.

Instead, two filters applied only on the flow's own profiled request:

```php
add_filter( 'woocommerce_order_needs_payment', '__return_false', PHP_INT_MAX );
add_filter( 'woocommerce_cart_needs_payment',  '__return_false', PHP_INT_MAX );
```

Nothing is created, the cart totals are untouched so shipping and tax calculate in full, and
the order total stays real - £16.00 on the docker store - so downstream integrations see a
normal order. The checkout takes `process_without_payment()`, which calls `payment_complete()`
and runs the entire post-payment cascade: status transition, stock reduction, order emails and
every integration hooked onto them. That cascade is 328 queries on a stock WooCommerce store
with no third-party plugins at all, which is the number this feature exists to attribute.

The gate is written as a **whitelist** of payment modes allowed to take a payment
(`SSPA_Checkout_Flow::PAYMENT_MODES`, currently empty), never as "not sandbox". A missing,
unknown or future flag value falls through to no payment, because getting the default wrong in
the other direction charges someone real money. Case 19 asserts this through the real
armed-request path for three flag shapes - absent, junk, and `pm=s` with no adapter registered
- using a new `npc` probe that reports `needs_payment()` on an in-memory £47 order, so nothing
is created to answer the question.

### A real cart, not an empty one

The first working build had `flow-view-cart` and `flow-view-checkout` rendering an empty cart,
with the checkout page answering 302 and bouncing back to the cart, because the Store API keys
its session to the `Cart-Token` header and never sets a front-end session cookie. That would
have reproduced the exact flaw the feature exists to fix, while looking like a clean run.

WooCommerce 11's `WC_Session_Handler::init_session_from_request()` restores a guest session
from a cart token supplied as `?session=`, for `t_`-prefixed customer ids only. So the first
page view after add-to-cart carries the token and every later one reuses the cookie that came
back - one session for the visit, as a real customer would have, rather than a fresh clone per
page. The session rows the run creates are deleted again by key when it finishes.

The default product also changed: the cheapest purchasable simple product on the WooCommerce
sample dataset is "Single", which is downloadable, so shipping never calculated and
`flow-select-shipping` was skipped. `default_product()` now prefers the cheapest product that
`needs_shipping()`, and only falls back to a virtual one when the store sells nothing physical.
An explicitly requested product that cannot be bought now returns `no_product` rather than
quietly substituting a different one - a silent substitution is a wrong answer that looks like
a right one.

### The disclosure, and what the run leaves behind

The run buys something for real, so the admin sees exactly what it will set off first.
`SSPA_Checkout_Preflight::inventory()` runs on the FRONT END inside a profiled probe, because
an inventory taken from a wp-admin screen misses every front-end-only hook registration. It
reports the enabled transactional emails and their recipients, whether emails are deferred or
sent in-request, active webhooks reduced to their delivery HOST (the full URL routinely carries
a secret and this list is shown on screen), and every component that will run code on the six
order-lifecycle hooks, resolved by reflecting each callback back to its defining file through
the existing component map. Case 19 proves that resolution works on a closure defined in a
planted fixture plugin.

Block-versus-classic detection uses `CartCheckoutUtils::is_checkout_block_default()` rather
than `has_block()` against page content, because a block theme template can supply the checkout
block without it appearing in `post_content`.

Cleanup is layered, because an orphan order in a customer's store is the one outcome this
feature must never produce:

1. every order is stamped `_sspa_temp` as it is created, both by an in-request hook and by the
   driver the moment it learns the id,
2. the id goes into the `sspa_flow_temp` option before the next request goes out,
3. deletion runs in a `finally`, never on the happy path, so any failure after an order exists
   still deletes it,
4. the delete probe and the driver both re-check `_sspa_temp` before deleting anything,
5. the hourly janitor sweeps both the option and any `_sspa_temp` order over an hour old, in
   `wp_postmeta` and the HPOS `wc_orders_meta` table.

Stock is verified rather than assumed. The design doc flagged "cancelled-then-deleted restores
stock" as unconfirmed, so `verify_stock()` compares before and after, puts the number back
explicitly if it has to, and records that it was needed. On WooCommerce 11 it has not been
needed; the check stays because the alternative is trusting it.

### Mail is really sent, for this run type only

> * Order emails are sent for real during a checkout flow run so your mail server's own time is
>   measured; every other kind of run still sends nothing.

Construct mode measures the wrong half for checkout: it builds the message (template cost) and
strips the recipients before transport, so a slow SMTP handshake - a classic reason a checkout
takes four seconds, and squarely in scope - is invisible. The capture gains a third mode,
`deliver`, which intercepts nothing, alters nothing and only times.

One deviation from the design doc. It specified hooking `wp_mail`, `wp_mail_succeeded` and
`wp_mail_failed`. An API mailer that short-circuits `pre_wp_mail` fires neither of the latter
two, so the very case the `wp_mail` hook was chosen to cover would have recorded nothing.
Deliver mode therefore also hooks `pre_wp_mail` at `PHP_INT_MAX` and closes the pending entry
when the incoming value is non-null, and `finalize()` records a still-pending send with an
unknown duration rather than dropping it, because a missing call reads as "no mail was sent".

This deliberately opens a hole in an invariant the plugin otherwise keeps absolutely, so
`mail=d` is reachable only from the checkout flow, whose tokens are minted after an
administrator accepted the disclosure, and it is not the default of any other run type.

### Findings

Five checkout-specific types, with thresholds in the rules feed rather than hard-coded
(`checkout_slow_step_ms` 800, `checkout_component_share_pct` 25, `checkout_http_ms` 50):
`checkout_slow_step`, `checkout_component_cost`, `checkout_blocking_http`,
`checkout_mail_inline` and `checkout_dupe_queries`. They run from
`SSPA_Analysis_Engine::analyse_checkout()`, a separate entry point from `analyse()` because a
flow run has no pages, one sample per step and no baseline, so the page heuristics either do
not apply or would compare against nothing. The pre-flight and delete steps are excluded from
every total there, exactly as they are in the panel.

`checkout_blocking_http` is the one that earns its place: a blocking outbound call inside
place-order or the address step is the classic cause of a six-second checkout. Case 19 plants a
fixture that calls back into the site on `woocommerce_payment_complete` at an endpoint which
sleeps 150ms, and asserts the finding names that plugin - a real call with a repeatable
duration, rather than one that trips the threshold by luck.

### The panel

Waterfall in flow order with the slowest step marked, split into an at-risk half and a secured
half, with the delete step measured but sitting below the total and excluded from it (nobody
waits for admin cleanup). Below that: the findings, mail count with whether it was in-request
or deferred, every outbound call with host and duration, per-component PHP time across the
whole purchase from the Excimer roll-up, and the safety report - orders deleted, orders left,
stock before and after.

It renders into the same popover container as the ad-hoc panel, so it inherits that panel's CSS
wholesale and only its own `sspa-ck-*` additions were needed; interactive elements use
`sspa-ck-*` class names so the two scripts' delegated handlers cannot collide.

`SSPA_Checkout_Flow::rollup_profile()` sums each step's Excimer report by component and by
function. Two limitations are printed rather than hidden: each step's report is already
truncated to its top 40 functions, so this is a sum of top-N lists rather than a whole-flow
profile, and inclusive time cannot be added to self time to make a total. The sampler's own
sanity check - sampled ms against summed step generation time - came out at 0.95 on the docker
run, and case 19 asserts it stays between 0.3 and 1.5.

`SSPA_Excimer::phase_windows()` also stopped labelling the final window `render_and_output` on
REST and `wc-ajax` requests, where there is no template and that window holds nearly everything
the endpoint did. It is now `endpoint_work` there, which matters most on exactly the requests
this feature measures.

### Tests

`.tests/cases/19-checkout-flow.php`, 54 assertions, driving
`SSPA_Run_Controller::start(['type' => 'checkout'])` and the batch loop - the same entry point
the button uses, never a hand-assembled sequence of steps.

## 0.10.11 (7th August 2026)

### The plugin never checked for its own updates

> * Restored the plugin's own update check against superspeedyplugins.com, so new versions
>   show up on your Plugins screen again. If you are on 0.9.3 to 0.10.10, install this one

Found while verifying the 0.10.10 release zip in a clean Docker WordPress 7.0.2 playground -
the brief was "confirm the super-speedy-settings submodule is correctly configured", and it
was not.

**The symptom.** No update was ever offered for this plugin, from any version, on any site.
Nothing failed and nothing was logged; the Plugins screen simply never listed an update.

**The cause.** Settings 1.5.0 (2026-08-03, the candidate-registry "latest copy wins" loader)
turned `super-speedy-settings.php` into a thin facade. It no longer defines anything real -
it queues the copy as a candidate and lets the NEWEST registered copy's
`super-speedy-settings-core.php` load at `plugins_loaded` priority -9999. The PUC library is
required by that core, at line 19.

This plugin required the submodule and then, on the very next lines of its main file, did:

```php
if (class_exists('SuperSpeedy\PluginUpdateChecker\v5\PucFactory')) {
    $sspa_update_checker = PucFactory::buildUpdateChecker(...);
}
```

Plugin main files are included long before `plugins_loaded` fires, so from the moment this
plugin picked up the facade-era submodule that `class_exists` was always false and the
update checker was never built at all. The guard was written for "a zip without submodules",
and it silently absorbed a completely different failure. First affected commit: e2a9cbc
(3rd August 2026), plugin version 0.9.3.

The paid plugins are not affected. They call `SuperSpeedySettings::init()`, and the core
builds their update checkers itself (`super-speedy-settings-core.php:171`) once it has
loaded. This plugin deliberately skips `init()` - it is free, has no licence key, and a
second registration of the same slug fatals PUC - so it is the only one building its own,
and the only one that had to care when the load order changed.

**How it was proven, not assumed.** Reading the code gives you the hypothesis; the evidence
came from the real code path. A `pre_http_request` logger in a mu-plugin recorded every
outbound URL during a genuine logged-in `wp-admin/plugins.php` request with the update
transients cleared. Result: `api.wordpress.org` only (which does not carry this plugin) and
`sspa_update_checker: NOT BUILT`. Positive control - the same harness, with a mu-plugin
building the checker at `plugins_loaded` -9998 - fetched
`https://www.superspeedyplugins.com/assets/plugins/super-speedy-performance-analysis.json?installed_version=0.10.10&php=8.3.32...`,
confirming the harness can see a working checker and that the load order was the whole
difference.

**The fix.** The build moves into an `add_action('plugins_loaded', ..., -9998)` callback -
one tick after the core registers at -9999 - and stores the checker in
`$GLOBALS['sspa_update_checker']`. The `class_exists` guard stays, so a zip genuinely
missing the submodule still activates and simply goes without update checks.

**What this means for installed sites.** Any site on 0.9.3 to 0.10.10 has no working update
mechanism, so it cannot be told about 0.10.11 - the fix cannot reach those sites through the
thing it fixes. They need one manual install, after which the checker is live. Sites still on
0.9.2 or earlier bundle a pre-facade submodule, so their update check works and they will be
offered 0.10.11 normally, provided
`/assets/plugins/super-speedy-performance-analysis.json` on superspeedyplugins.com is
updated to 0.10.11.

## 0.10.10 (7th August 2026)

### The plugin-toggle spot-check looped forever

> * Fixed the spot-check offered after you activate or deactivate a plugin re-running
>   itself every time the page reloaded, instead of stopping once its results were in.

**The symptom.** Reported by Dave against live superspeedyplugins.com. Activate a
plugin, take the "want a 30-second performance spot-check" offer in the admin notice,
land on `admin.php?page=sspa&sspa_autospot=1#overview` - and the page reloads and
re-runs the analysis over and over, with no way out but editing the address bar.

**The cause.** Two pieces of behaviour that are each correct alone. `sspa_runner_finish()`
ends EVERY run with `window.location.reload()`, because the results tabs are rendered
server-side and a reload is how they refresh. And the autospot trigger in the
document-ready handler keys off `window.location.search`, which the reload preserves
verbatim. So a finished autospot run reloaded a URL still carrying `sspa_autospot=1`,
the ready handler saw the flag again and started a fresh run, that run finished and
reloaded, and so on indefinitely. Nothing in the loop was rate-limited: each iteration
profiled home, shop and baseline for real.

The `active-run` guard did not help. It only re-arms the monitor for a run that is still
going; by the time `sspa_runner_finish()` fires, the run is complete, so on the reload
`active` is 0 and control falls through to exactly the `else if` that starts another one.

**The fix.** The flag is consumed once, at page load: `sspa_strip_autospot_param()` reads
it into a local, then removes it from the address bar with `history.replaceState` before
any run is started, preserving the rest of the query string and the `#overview` hash. The
post-run reload therefore lands on a clean `admin.php?page=sspa#overview` and stops. The
strip happens before the active-run branch too, so a reload during an in-flight autospot
run cannot leave a live flag behind either. Browsers without `history.replaceState` (none
that run WP 6.2 admin) simply keep the old behaviour rather than erroring.

Second, smaller half: the `sspa_plugin_toggled` transient was only deleted by the Dismiss
link, so for its full 10 minutes the notice kept offering a spot-check you had already
taken - and every one of those offers was another entry into the loop. Arriving with
`sspa_autospot` now deletes the transient as well, in `toggle_prompt_notice()`.

## 0.10.8 (4th August 2026)

### Measurement-path disclosure

Dave's MaxMind rows persisted after enabling Cloudflare IP Geolocation, prompting "is
this a WooCommerce bug or a perf-tool bug?". Answer: likely neither - a measurement-path
divergence. SSPA's profiling requests are server-to-self loopbacks; when the host pins
the domain locally (GridPane commonly does), they bypass Cloudflare entirely and arrive
with NO CDN-added headers. WooCommerce then correctly runs MaxMind on the measured path
while real visitors (whose requests carry CF-IPCountry) correctly skip it. The tool was
honestly measuring a path visitors do not take, and saying nothing about it.

Fix: the capture (which runs INSIDE the profiled request) records
`overview.via_cloudflare` (HTTP_CF_RAY present) and `overview.cf_country`
(HTTP_CF_IPCOUNTRY). The panel renders one of:

- "went directly to origin, not through Cloudflare - CDN-added headers were absent;
  costs that only occur without them (such as WooCommerce's MaxMind lookup) may not
  apply to real visitors"
- "profiled through Cloudflare (visitor country header: XX)"
- "profiled through Cloudflare - no visitor country header; IP Geolocation is off in
  Cloudflare" (the toggle genuinely off case)

One re-run distinguishes the three states with data instead of inference.

## 0.9.14 (4th August 2026)

### Expandable phases

Dave's question "can these be expanded?" had a pleasing answer: the data was already in
every capture - `boot.hooks` (per-hook per-component ms), `boot.includes` (per-plugin
file load) and `boot.render.components` all ride the ajax payload - the popover just
never showed them. `phaseDetail()` maps each phase to its source (`plugin_includes` ->
includes; `plugins_loaded_callbacks` -> hooks.plugins_loaded; `init_callbacks` ->
hooks.init + hooks.widgets_init; `post_init_boot` -> hooks.wp_loaded +
hooks.rest_api_init; `theme_load_and_setup` -> hooks.after_setup_theme;
`render_and_output` -> render.components). Phase rows with detail get a caret and
pre-rendered hidden subrows (top 12 by ms); the difference between the wall-clock phase
and the timed detail is shown as "untimed / core framework" (or "theme templates +
direct output" for render). Core-before-plugins and routing have no per-component data
and render as plain rows. Because the sources were always captured, expansion works on
EXISTING stored results.

### Shrinking the untimed render remainder

Two new instruments, both feeding the render ledger:

- **WooCommerce layout hooks** join the wrapped list (before/after main content, shop
  loop + item hooks, single product summaries, sidebar). Anything `woocommerce_*` in
  the wrapped list is render-phase by prefix (`is_render_hook()`). No-ops without Woo.
- **Dynamic block timing**: `pre_render_block` (PHP_INT_MIN) pushes, `render_block`
  (PHP_INT_MAX) pops a LIFO stack; only blocks with a `render_callback` are tracked
  (static blocks are stored HTML), only OUTERMOST dynamic blocks are recorded (an inner
  block's time is inside its parent's - recording both would push the ledger past the
  segment), and attribution reflects the block's render_callback to the providing
  plugin's file.

Docker effect: home's render phase went from 32% timed (10 of 31.6ms) to 69% timed
(32.5 of 47.1ms). What remains untimed is genuinely the theme's own template code -
decomposing THAT needs function-level profiling (roadmap phases 5-6).

### Double-wrap fix (latent since 0.9.10)

`wrap_pending()` ran on EVERY firing of a hook. the_content and the Woo loop hooks fire
once per post/item, so each firing re-wrapped the already-wrapped callbacks - nested
timers recording the same work at every layer. On archive pages the render ledger could
overcount several-fold (masked by the untimed_ms >= 0 clamp). Now guarded once per
hook: the wrappers persist and time every subsequent firing; only the wrapping itself
happens once. Callbacks registered after a hook's first firing go untimed - acceptable
and documented.

## 0.9.9 (4th August 2026)

### The phase table must account for the whole request

Found by Dave on live within minutes of using the popover: shop reported ~700ms
generation but the visible phases summed to ~400ms. The segment pairs in
`SSPA_Boot_Timer::segments()` ended at `template_redirect`, so the entire template render
- the biggest phase of a WooCommerce page - had no row, and neither did
`init_done -> wp_loaded`. A table that accounts for only part of the time invites exactly
the wrong conclusion ("the rest must be unmeasurable").

Fix: `report()` stamps a `request_end` milestone (it already runs in the capture's
shutdown handler, after output), `segments()` gains `post_init_boot`
(`init_done -> wp_loaded`) and `render_and_output` (last accounted milestone ->
`request_end` - which on wp-admin pages, where `template_redirect` never fires, correctly
covers the screen render from `wp_loaded`). Both JS renderers name the new rows. Case 17
now asserts the segments sum to within 15% of `gen_ms`.

Note the render phase is a single number for now: per-plugin attribution inside render
(shortcodes, widgets, template parts) is future work - the SQL/HTTP tables already cover
its database side.

## 0.9.7 (3rd August 2026)

### Bootstrap decomposition - the PHP-floor instrument

Driven by the live investigation: run 4 showed every anonymous page on
superspeedyplugins.com paying a ~500ms PHP floor (including the 404 - so bootstrap, not
content), and deep run 5's 66-plugin sweep could not decompose it: no single exclusion
moved any front-end page more than ~80ms, because the floor is 66 plugins each costing
slices below the noise gate. Single-out exclusion is structurally blind to
death-by-a-thousand-cuts. The alternatives (excimer/xhprof) need PECL installs most
customers cannot do.

New `profiler/class-sspa-boot-timer.php` (standalone, armed-request-only), installed by
`SSPA_Capture::arm()` - which runs from the mu-loader, before any regular plugin loads,
the only vantage point from which per-plugin include timing is possible:

- **Per-plugin include timing**: core fires `plugin_loaded` after each plugin file;
  deltas between events = that plugin's include + top-level cost. First plugin absorbs
  core's small l10n setup (approximate, documented).
- **Milestone ledger**: `muplugins_loaded`, `plugins_loaded` (PHP_INT_MIN/MAX), `init`
  (MIN/MAX), `after_setup_theme`, `wp_loaded`, `template_redirect` - derived into named
  phases (core boot, plugin includes, plugins_loaded callbacks, theme setup, init,
  routing/query).
- **Per-callback hook timing**: for each profiled hook (`plugins_loaded`,
  `after_setup_theme`, `init`, `widgets_init`, `wp_loaded`, `wp_enqueue_scripts`,
  `admin_init`, `admin_menu`, `admin_enqueue_scripts`, `template_redirect`,
  `rest_api_init`), a PHP_INT_MIN callback wraps every later-priority callback in a
  timing closure AS THE HOOK STARTS. WP_Hook reads each priority bucket live, so
  mutating buckets it has not reached is safe, and wrapping from inside the hook catches
  callbacks regardless of when they were registered (the failure mode of wrap-early
  approaches: WooCommerce registers most of its init work during plugins_loaded).
  Each callback is attributed via reflection + the component map at report time.

Capture gains a `boot` section (`segments`, `includes`, `hooks`, `components` - the
combined per-plugin ranking of include + callback ms - and `top_callbacks`); stored in
the existing profile blob, no schema change. `ajax_page_detail` passes it through and
the Pages drill-down renders three tables: request phases, PHP cost per plugin, slowest
callbacks.

Verified in docker (05-run-e2e, new assertions): WooCommerce include timed and
attributed, init callbacks timed, page renders identically with every callback wrapped.

Overlap caveat, stated in the class docblock: a plugin's include time and its hook
callback time are separate rows of one story; hook totals must not be blindly summed
with segment totals.

## 0.9.6 (3rd August 2026)

### Deep-analysis fatals must not trigger WordPress's recovery-mode email

Live incident during the first real deep run (run 5 on superspeedyplugins.com): isolating
`woocommerce-subscriptions` and profiling admin-orders-search made WooCommerce's
`WC_Order_Factory::get_orders()` throw ("Could not find classname for order ID 7503" - a
subscription order whose `shop_subscription` type wasn't registered with Subscriptions
excluded). The 500 happened ONLY inside the signed, plugin-set-filtered test request -
no visitor could ever see it, WooCommerce was never a candidate for exclusion (verified:
0 of the run's 66 isolation payloads contained it; `Requires Plugins` roots are barred by
`SSPA_Dependency_Map::isolation_candidates()`), and `sweep_deltas()` already refused the
cell (`response_code < 500` gate) so no impact number was polluted.

But core's `WP_Fatal_Error_Handler` caught the fatal and emailed the admin a scary
"technical issue" recovery-mode message blaming WooCommerce - the file that threw, not
the plugin that was excluded. Fix: the mu-loader defines `WP_SANDBOX_SCRAPING` on every
token-verified request; core's handler short-circuits on it (its own mechanism for
plugin-editor loopback sandbox tests, and its only reader in core), so profiled-request
fatals neither email nor trip recovery mode. Real traffic never reaches the mu-loader's
token path, so its protection is unchanged.

### Fatal cells surfaced as discovered dependencies

`sweep_deltas()` marks an unresolved cell `fatal` when it 5xx'd with a healthy baseline;
`finish_sweep()` collects them into the run notes as `fatal_cells` and the Overview's
deep panel renders them: plugin + page, with the explanation that this is a hard runtime
dependency discovered by experiment, that only the analysis's own requests saw the
error, and that any WordPress "technical issue" email during the run was this - usually
blaming the plugin whose file threw rather than the excluded one.


### Resolve permastruct placeholders in CPT archive URLs

Found by run 4 on live (the first 0.9.4 run): its single unmeasured page was
`cpt-kb-archive`, catalogued at the literal URL `/kb/%kb_category%/`.
`get_post_type_archive_link()` returns the permastruct TEMPLATE, placeholder and all, for
a CPT whose rewrite embeds a taxonomy. The request runs PHP (600ms walls observed), but
the `%` signs are re-encoded in transit, so `REQUEST_URI` no longer matches the token's
signed path - the mu-loader stays inert, no canary, every sample wasted as `no_canary`.

Fix in `SSPA_Catalogue`: `resolve_permastruct_tokens()` substitutes each `%token%` whose
name is a real taxonomy with that taxonomy's biggest term (by count, hide_empty), and
returns null - page skipped - when a placeholder cannot be resolved. Note for a KB-style
CPT the resolved archive URL coincides with the `tax-kb_category` page; the duplicate
measurement is accepted rather than special-cased.

All four changes fall out of one comparison: two baseline runs on live
superspeedyplugins.com, run 1 with Query Monitor active (riding its db.php), run 2 with QM
deactivated but - unknown at the time - its db.php drop-in still in place. The two runs
disagreed everywhere, and each disagreement was a bug.

### Cache-busting profiling requests

**Symptom:** home, shop, product-single and every other pretty-URL anonymous page had NULL
metrics in both runs, with samples recording `error: no_canary` and wall times of 11-24ms -
a full-page cache answering. The only pages that profiled were the ones a cache never
serves: query-string URLs (`?s=`, the probes, the randomised 404 URL) and the
cache-excluded WooCommerce endpoints. The run then completed "done" and scored the site
off the unrepresentative remainder.

**Cause:** the profiling token travels in the `X-SSPA-Token` request header, and the
crawler sent `Cache-Control: no-cache` as a request header. Page caches key on the URL and
vary on neither, so nginx fastcgi_cache served the stored HTML and PHP (and the
mu-loader canary) never ran.

**Fix** (`includes/class-sspa-crawler.php`):

- Every signed request now appends `sspa_nc=<12 hex chars>` via `bust_url()` - a unique
  URL per request guarantees a cache MISS on anything that keys on the URL. The token
  signature already binds to path+query (`SSPA_Token::request_path()`), so the arg is
  minted into the signature and cannot be stripped or replayed onto another URL. Redirect
  hops re-bust (add_query_arg replaces the previous value); the signed warm-up used by
  isolation/cache-off jobs busts too. The unsigned warm-up deliberately does not - warming
  the cache is its job.
- `looks_cached()` now also recognises `x-fastcgi-cache`, `x-vercel-cache`, `x-qc-cache`
  and a non-zero `Age` response header.

`mu/sspa-loader.php` additionally sends `Cache-Control: no-store, no-cache,
must-revalidate, max-age=0` on every token-verified response: a profiled response stored
by a cache would be served to real visitors and would answer later profiling requests
without running PHP. (Template change - reinstalled automatically by `ensure_installed()`
on the next admin page load because the generated content differs.)

### Attribution: skip the db layer

**Symptom:** 100% of queries in BOTH runs attributed to `query-monitor` (17,586 and
18,378 queries respectively); every other component at zero. Findings evidence showed
`"caller":"QM_DB->query (DB.php:0)"` - including in run 2 where QM was not an active
plugin.

**Cause:** when parsing QM-format `$wpdb->queries`, `attribute_from_summary()`
(`profiler/class-sspa-component-map.php`) resolves callable names to files by reflection.
`QM_DB->query` is the innermost resolvable frame of every stack, it resolves into
`plugins/query-monitor/`, and `chain()` had no concept of "the db layer is transport, not
spender" - it skips core and our own frames only.

**Fix:** `is_db_layer()` - a cached reflection check that skips any frame whose class is
`wpdb` or a subclass of it (QM_DB, LudicrousDB, anything else). Applied in
`attribute_from_summary()` before file resolution. The frames-based path (our own
profiling wpdb) never had the bug: our frames are own-dir and already skipped.

### Honest drop-in health + stale-QM handling

**Symptom 1:** run 1 (QM plugin active) captured full per-query data on logged-in admin
pages but NOTHING on anonymous pages - QM only collects when the viewer could see its
output. The Overview meanwhile claimed "riding Query Monitor's db.php - full detail
available", and the swap checkbox was only rendered for `foreign` drop-ins, never `qm`
(the backend honoured `swap_dropin` for both all along).

**Symptom 2:** deactivating QM left its db.php behind (an orphan that still executes
standalone), `ensure_installed()` correctly refuses to overwrite a foreign file, and
nothing anywhere said so.

**Fixes** (`class-sspa-helper-files.php`, `tabs/overview.php`, run controller AJAX):

- `qm_plugin_active()` / `dropin_is_stale_qm()` / `replace_stale_qm_dropin()` - the
  replace renames the orphan to `db.php.qm-stale-<timestamp>` (never deletes) and installs
  ours; QM reinstates its own copy if reactivated.
- Health surfaces `stale_qm` and `qm_active`. Overview: active QM gets a warning
  (anon capture missing, backtrace overhead) plus the swap checkbox; stale QM gets a red
  line and a one-click "Replace it with ours" button (`wp_ajax_sspa_replace_stale_dropin`).

### Unknown is not zero

**Symptom:** run 1's blind anonymous pages stored `sql_ms = 0`, `rows = 0`,
`dupe_query_count = 0` - indistinguishable from a page that genuinely spent no time in
SQL, and `php_ms` silently absorbed the entire generation time.

**Fix:** `collect_sql()` (`profiler/class-sspa-capture.php`) returns null for
`total_ms`/`rows_total`/`dupe_count` in `mode === 'none'` (the query count stays - it
comes from `$wpdb->num_queries` and is real). `SSPA_Profile_Store` only derives `php_ms`
when both gen and sql are known. `finish()` counts profiles with NULL `page_gen_ms` (and
no `blocked_by`, excluding baseline/mail-probe) into the run notes as `unmeasured_pages`;
the Overview shows a red incomplete-run notice and the Pages tab marks each such row
"not measured - cache served it".
