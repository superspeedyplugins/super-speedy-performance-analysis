# Super Speedy Performance Analysis - full engineering changelog

Long-form companion to the customer-facing changelog in `readme.txt`. Newest first.

## 0.23.4 (17th August 2026)

### Order completion read back stale on cached sites

> * Fixed the checkout flow reporting an order's completion transition as `processing` to
>   `processing` on sites with a persistent object cache

**The symptom.** The checkout flow's order-management step marks the synthetic order
completed inside a profiled loopback, then reads the status back to name the transition on
the panel. On a site with Redis or Memcached in front of the object cache, the read-back saw
`processing` even though the order had genuinely completed - the panel said
"processing -> processing", the waterfall carried the wrong label, and
`.tests/cases/33-order-management.php` failed on exactly those three assertions.

**The cause.** The read-back busted `wp_cache_delete($order_id, 'orders')` before calling
`wc_get_order()`. WooCommerce does not key orders by bare id: HPOS caches them as
`orders:wc_cache_<prefix>_<id>`, where the prefix comes from a stored, rotating value. The
delete removed a key that never existed - a no-op since the day it was written. Confirmed by
dumping the Redis keys for a test order and by a probe: the plugin's busting read stale,
`WC_Cache_Helper::invalidate_cache_group('orders')` (which rotates the prefix) read fresh,
and `wp_cache_flush()` read fresh.

**Why it survived so long.** Without a persistent object cache every process starts empty, so
the stale read cannot happen. The Docker test environment had no object cache; the native
test site gained Redis on 16 August and the bug surfaced the same day. The affected sites are
precisely the performance-conscious ones this plugin targets.

**The fix.** `class-sspa-checkout-flow.php` now also calls
`WC_Cache_Helper::invalidate_cache_group('orders')` before the read-back. Case 33 pins it.

### Plugin Check: 418 errors to zero

> * Cleared every Plugin Check (PCP) error: table names now go through `$wpdb->prepare()`'s
>   `%i` placeholder, admin output is escaped, and translatable strings with placeholders
>   carry translators comments

PCP reported 418 errors in the plugin's own shipped code. All cleared, none waived silently:

- **253 SQL errors**: every interpolated `SSPA_Schema::table()` moved into
  `$wpdb->prepare()` with the `%i` identifier placeholder (WP 6.2+, already the floor).
  ~150 call sites across 22 files. `latest_impacts_sql()` now returns a fully prepared
  string; its four callers carry a `phpcs:ignore` naming that fact. Two genuinely dynamic
  sites keep justified ignores: `EXPLAIN <captured SQL>` in `class-sspa-explain.php` (the
  SQL is the subject) and the observer's generated INSERT (prepared, but through a variable).
- **31 filesystem errors** (`unlink`/`rename`/`is_writable`/`chmod` on the db.php drop-in and
  mu-loader): per-site `phpcs:ignore` with reasons, after verifying Query Monitor ships on
  wp.org doing exactly this - rename() is atomic where `WP_Filesystem::move()` is not, and a
  half-swapped db.php takes the site down.
- **72 missing translators comments** written, **16 unescaped admin outputs** escaped,
  **13 `parse_url` -> `wp_parse_url`**, 8 profiler files gained `ABSPATH` guards, abilities
  registration gained `function_exists` guards for the WP 6.9+ Abilities API.

Two self-inflicted bugs caught during the sweep, both now covered by
`.tests/cases/46-admin-tabs-render.php`: 17 translators comments initially landed OUTSIDE
`<?php` blocks in the tab templates (they would have rendered as page text), and `%1$s` in a
double-quoted string interpolated `$s` and broke the performance_schema host message.

Verified end to end after the rewrite: full analysis run, deep sweep, all admin tabs, and
filter assertions that discriminate (including an injection string staying a literal).
`.tests/cases/45-sql-identifiers.php` pins the behaviour.

### DISALLOW_FILE_MODS

> * Sites that set `DISALLOW_FILE_MODS` are respected: no helper files are written, and the
>   health line and run errors name the constant instead of file permissions

Gates creation only: `ensure_installed()`, both drop-in hold paths,
`replace_stale_qm_dropin()` and the traffic observer installer refuse when the constant is
set. Removal is deliberately ungated - refusing it would strand a db.php the owner cannot
remove from the UI. `health()` carries a `file_mods_blocked` flag so the Overview line and
the run-blocking `WP_Error` name the real cause; the old message sent people to chmod a
directory whose permissions were fine. Same split Query Monitor uses for its db.php symlink.
`.tests/cases/44-file-mods-disallowed.php` pins all of it, with a negative control.

### wordpress.org edition build

> * Added a wordpress.org edition build that omits the bundled update checker

`.build/` produces two zips from one tree: full (with the `super-speedy-settings` submodule
and PUC updater) and wp.org (without). Deleting the submodule is not enough - PCP's
plugin-updater check is a string scan, so even the `class_exists('...PucFactory')` guard in
the main file is an error. The self-hosted updater block is fenced with
`SSPA-SELFHOSTED-UPDATER-START/END` markers and stripped by the wp.org hook; build
assertions fail if the markers go missing, any `PucFactory` reference survives, or the
`add_menu_page()` fallback disappears (the wp.org zip would otherwise install with no admin
menu). Both editions PCP-clean and smoke-tested; the wp.org zip runs a full analysis on a
disposable site.

### PHP 8.1-8.5 matrix, and the Excimer verdict

> * Tested the full suite on PHP 8.1 through 8.5

Run on a dedicated Ubuntu 24.04 amd64 test server (Ondrej packages), five parallel
sites, one per version, each with WooCommerce + HPOS + Redis + excimer, wp-cli and php-fpm
version-matched. Result: 44/44 cases on 8.1 and 8.2; 43/44 on 8.3/8.4/8.5 where the one
failure is `12-agents.php` dying inside `WP_CLI::runcommand(launch => true)` -
`stream_get_contents(): Argument #1 must be of type resource, null given` in wp-cli 2.12.0
on PHP 8.3+. The plugin's CLI is fine on every version when invoked directly; the test's
transport is what breaks, not the surface under test.

Excimer: over 1.26M samples collected across the five versions with zero fpm crashes. That
closes the investigation the MacBook opened - excimer 1.2.6 AND upstream 1.2.7 both segfault
php-fpm on macOS/arm64/Homebrew (8, 12 and 14 crashes across three full-suite runs), so the
Mac is the outlier and case 18 fails there by design rather than being skipped. Full data:
`.tests/README.md`; the per-version raw results live on the test server.

Three harness lessons from the matrix, recorded because each looked like a plugin bug: the
suite must run against the repo, not the built zip (fixtures live in `.tests/`, which the
zip strips); wp-cli must run as `www-data` so files it writes stay writable by php-fpm
(root-owned observer files silently lost the traffic collector's stop reason); and a runner
counting PASS/FAIL lines scores a mid-case fatal as a pass - the matrix runner now detects
fatals explicitly.

### Test suite off Docker

No readme entry - development-facing. `.tests/docker/` is gone; the suite runs on a native
parallel-dev site built by `.tests/setup-site.sh` (WooCommerce, HPOS, coming-soon off, Redis,
sample data), with `env.sh` deriving paths from parallel-dev so the WSL2 box works too. Three

## 0.21.2 (13th August 2026)

### `complete` was the wrong question for archive configuration

> * An archive page that could not be profiled no longer stops Super Speedy Archives configuring
>   itself when the pages it needed were measured.

`complete` answers "did every page in the catalogue succeed". Super Speedy Archives gated its
configuration on it, so one blocked page anywhere refused configuration for the entire site. On a
client running security hardening - the same site that returned 403 on `wp-json/wp/v2/users/me` -
that is a permanent block, not an occasional one.

Reproduced by marking the **404 page** as blocked on an otherwise perfect run: `complete` went
false and Archives refused. A 404 page cannot contain a front-end archive. Its absence says
nothing whatever about archives.

The profile now also reports `archive_evidence_complete`, false only when a page that could hold
an archive was missed, and `incomplete_pages` naming which classes were affected so a consumer can
explain itself. `complete` keeps its meaning and its name - it is a fair thing to report, and the
wrong thing to gate archive configuration on.

Archive-capable page keys are listed explicitly in `$archive_page_keys`, with custom post type and
taxonomy archives matched by prefix. Everything absent from that list is absent on purpose.

This is the third bug of the same shape in four releases - 0.19.1 (probes counted as failures),
0.21.1 (a flaky sample discarding a good capture), and now this. The pattern each time was
inferring "the evidence is unusable" from something broader than the evidence actually needed.

## 0.21.1 (13th August 2026)

### Sharing metadata must never stop an analysis

> * An analysis now starts even when collecting another plugin's published settings fails,
>   instead of the analysis failing with it.

A client site running 6.29.15 hit this on the Apply Good Settings button:

```
Uncaught Error: Call to undefined method SSPA_Community_State::disabled()
  in .../class-sspa-community-state.php on line 124
  SSPA_Community_State::collect()   class-sspa-run-controller.php:152
  SSPA_Run_Controller::start()      class-spro-analysis.php:74
  SPRO_Analysis::begin()            tabs/intro/functions.php:275
  spro_ajax_recommended_analysis()  admin-ajax.php:192
```

The immediate cause was a **truncated file** on that site, not a bug in this release: line 124 is
`self::disabled()` in 0.21.0, `disabled()` is defined at line 290, and the file is 449 lines. That
site had the first ~200 lines of the 0.21.0 file and nothing after, which a partial transfer
produces and a version mismatch does not - the 0.20.0 file is 282 lines and has a docblock at line
124.

The design defect it exposed is ours, and is the reason for this release. `start()` called
`SSPA_Community_State::collect()` unguarded, so anything that threw in there took down the whole
analysis. That is the wrong order of importance twice over:

1. Component state is metadata for SHARING. An analysis is what the plugin is for. A site with
   incomplete sharing metadata is a far smaller problem than a site that cannot measure itself,
   and a 500 on the button is the worst possible expression of the smaller problem.
2. `collect()` runs THIRD-PARTY CODE. Any plugin can register `sspa_component_state`. A fatal in
   somebody else's filter would have taken out the analysis button on every site running it, and
   we would have had no way to tell the site owner why. The per-record isolation added in 0.20.0
   protected the payload from one bad publisher; nothing protected the run itself.

Now wrapped in `try/catch (Throwable)` with `class_exists` and `method_exists` guards - `Throwable`
rather than `Exception` deliberately, because a broken filter raises `Error`. Failures are
recorded in `sspa_state_capture_errors` (last five) rather than swallowed: silence would mean a
payload quietly missing its component state with nothing anywhere to say why.

Verified by simulating the exact client fatal - a filter that throws that same `Error` - and
confirming the run starts, the message is recorded, and the analysis completes.

### The test that should have caught it

Every PHP suite in all three plugins was green while this was broken on a client site, because
they all called `SPRO_Analysis::begin()` directly and none of them pressed the button. A fatal
inside the AJAX handler is invisible from below it.

`scalability-pro/.tests/e2e/apply-good-settings.js` presses the button in a real browser, watches
all 51 steps through to "All done", and fails on any HTTP 500 or any `[Scalability Pro]` console
error even if the popover recovers and reaches the end. 18 assertions.

Two things it does that a naive version would not:

- The intermediate steps are observed WHILE they run. The result card replaces the step list on
  completion, so the first version "proved" the Archives step by matching the word "archive" on
  the final page - which it would have done whether or not the step ran.
- It bails the moment a 500 appears rather than waiting out the 15-minute timeout for a failure it
  already knows about.

Confirmed to fail on the real defect by dropping a probe that throws the same `Error` from the
analysis-start handler: both server-error and console-error assertions fire within seconds, with
the client's exact console line. The procedure is in `.tests/e2e/README.md`.

## 0.21.0 (13th August 2026)

0.20.0 let a plugin publish its settings and told the site's owner about it in a sentence that
named Scalability Pro and Super Speedy Archives by hand. That was consent theatre in two ways: it
was only true for the two plugins that happened to exist when it was written, and it gave the
owner no way to refuse one of them without refusing everything.

### The plugin says what it publishes, in the owner's language

> * The Share tab now lists every plugin publishing its own settings, in that plugin's own words,
>   with a switch for each one.

The filter's record gains a `disclosure` block - a `label` and a list of `publishes` lines. It is
**not submitted**. It is consent text: the receiver already has the keys themselves and has no use
for prose, and prose in a payload is a translation problem nobody needs. `collect()` strips it
before storage and case 37 asserts the string never appears in the encoded payload.

It is held to a different standard from the payload maps, because it is going on a screen rather
than into a JSON document: prose allowed, tags stripped, lines capped at 200 characters and 12 of
them, label capped at 64.

A plugin that declares nothing is **not** refused. Refusing would mean a plugin author's omission
silently removes their configuration from a payload the owner had already agreed to, which is a
worse failure than an unlabelled row. It is listed as `declared => false`, falls back to its slug
so the row is still identifiable, and the Share tab says in as many words that the plugin has not
described what it sends - which is a bug report the owner can act on.

### Per-plugin refusal

> * Switching a plugin off stops it publishing anything from your next analysis onwards; the rest
>   of your analysis is shared exactly as before.

`sspa_component_state_disabled`, an explicit deny list rather than an allow list, so installing a
new plugin does not start publishing under a decision made before it existed - and, for the same
reason, the Share tab lists every publisher rather than only the ones already in the list. A
consent screen that hides what you have declined gives you no way to change your mind and no way
to see the plugin is still installed and still asking.

**Applied at capture time**, in `collect()`, not at export. A switched-off publisher's
configuration is never written to `runs.share_context` in the first place. Filtering at export
would leave it sitting in the database of a site whose owner had declined to publish it, which is
the wrong place for it to be even if it never left. Case 37 asserts on the stored `share_context`
string, not just on the payload.

Deliberately independent of the site-wide sharing setting: an owner can let one plugin publish and
refuse another without turning sharing off altogether. It takes effect on the next analysis rather
than retrospectively - runs already measured keep what they captured, and the per-run preview
shows exactly what each one holds.

### Consent text that stays true

> * The consent text is built from what the installed plugins actually say they publish.

The paragraph naming Scalability Pro and Archives in `share.php` is gone, replaced by the
generated listing. `describe_payload()` now returns publisher labels rather than slugs, looked up
from the live plugins - so a payload whose publisher has since been deactivated falls back to the
slug, which is asserted rather than left to chance.

`CONSENT_VERSION` stays at 2. The scope of what can be shared has not widened; the owner has
gained control over a subset of it, and the wording describes the same maximum. Bumping it would
have re-prompted every site for a change that only ever narrows what they send.

### Tests

Case 37 grows from 35 to 53 assertions: the declaration surviving into the listing, an undeclared
publisher still being listed and marked as such, the switch recorded and reversible, a
switched-off publisher absent from the stored run context AND the payload, the publisher captured
again after being switched back on, and the consent text never reaching the wire.

One assertion caught a real ordering subtlety rather than a bug: labels come from the live plugin,
so the fixture filter has to be registered while the disclosure is rendered. That is the real case
- the Share tab renders on a site with the plugin active - and the deactivated case now has its
own assertion.

## 0.20.0 (12th August 2026)

A measurement that cannot say how the site was configured cannot explain itself. This release
lets other plugins publish their own configuration alongside a run, labels the two halves of a
before/after cycle, and records whether the site is real. Design in
`.docs/2026-08-12-component-state-evidence.md`; the as-built payload contract, which is what
superspeedy.org needs, is in `.docs/2026-08-12-component-state-payload-contract.md`.

### Declaration, not extraction

> * Other plugins can now publish their own performance settings alongside a shared analysis,
>   through the new `sspa_component_state` filter. A plugin only publishes what it deliberately
>   opts in to publishing; this plugin never reads another plugin's options.

The obvious implementation was to read the other plugin's option and ship it. That was rejected
on evidence, not on principle. On the development install, `superspeedy_options` for Scalability
Pro contains exactly one key and it is the licence key; `wpiperf_settings.sidebarcssselector` is
a free-text CSS selector the site owner types. Other plugins are worse: WP Rocket keeps CDN
hostnames and excluded URLs in its settings, LiteSpeed keeps a Redis host. And
`SSPA_Community_Privacy::validate()` aborts the entire payload on one forbidden value, so a
pass-through would not merely have leaked on those sites - it would have stopped them submitting
anything at all, with no visible cause.

So the plugin declares. `apply_filters('sspa_component_state', array(), $context)` fires once,
from `SSPA_Run_Controller::start()`, and registering the filter IS the opt-in. Each record
carries three deliberately separate maps: `summary` (the plugin's own verdict, groupable by a
receiver that knows nothing about it), `options` (raw detail, only meaningful with the version),
and `state` (runtime facts that are not settings). Merging them would force a receiver to know
which keys were which before it could trust any of them.

`SSPA_Community_State` enforces a flat value grammar - bool, int, float, null, a token string
matching `/^[A-Za-z0-9][A-Za-z0-9_.:, -]{0,127}$/`, or a list of those, capped at 8 records, 64
keys and 32 list members. The leading-alphanumeric requirement is load-bearing: it rejects
`.col-sm-3.col-sm-pull-9` while still admitting `02:00` and `6.29.14`. Anything dropped is
counted in `omitted_keys`, because a receiver must be able to tell "the plugin has no such
setting" from "the setting was censored on the way out".

Two things the grammar cannot do, both recorded in `.tests/cases/37-component-state.php` as
assertions rather than left as assumptions:

1. A secret shaped like an enum token (`ABCD-1234-SECRET-KEY`) passes. The filter decides WHICH
   keys travel; this plugin decides only what a value may LOOK like. That residual risk sits
   with the declaring plugin, which is the only code that knows what its own settings mean.
2. An IP address is alphanumerics and dots, so it passes the character grammar. The real privacy
   scanner is therefore run per key, so `server_ip` is censored on its own rather than costing
   the whole record.

Each record is then validated ALONE by `SSPA_Community_Privacy::validate()` and dropped on
failure. Without that isolation, one badly written third-party filter takes every submission
from that site with it, forever.

**Capture is at run start, into `runs.share_context`.** This is the part most likely to be
"simplified" later by someone who has not thought about it. Asking at export time produces a
perfectly well-formed payload that says the `before` run was measured with the settings that
were only applied afterwards - it inverts the exact comparison the evidence exists to support,
and nothing about the payload looks wrong. `component_inventory` is captured at run start for
the same reason. Case 37 changes a fixture's value between the run and the export and asserts
the payload carries the value from run start.

`component.version` is filled in by the exporter from the run's own inventory and never taken
from the filter, so a state record cannot disagree with the rest of the payload about what was
measured.

### Labelling the two halves of a cycle

> * The two halves of an Enable good settings run are now labelled `before` and `after` and
>   share a cycle identifier, so a shared pair can be compared as one experiment.

`run.change_cycle = {cycle_uuid, phase, driver}`. On the `run` object, not on a state record:
phase is a property of the MEASUREMENT, and two records in one payload could otherwise disagree
about which side of the change the run sat on. The UUID is minted for `before` and reused for
`after` by whichever orchestrator is driving - Scalability Pro's popover or the Archives tab -
and is random, so it identifies a pair and nothing else. An unrecognised phase is refused rather
than published.

### Is this a real site

> * A shared analysis now records whether the site is a production, staging, development or
>   local one.

`site_snapshot.environment.environment_type`, from WordPress's own `wp_get_environment_type()`.
A developer's laptop copy of a store measures the laptop: different hardware, no traffic, often
a partial database. A corpus that pools it with production is quietly wrong about every cohort
it contains.

Declared rather than inferred because inference would be poor - "localhost" is not a reliable
signal and a staging site usually looks exactly like the live one. Absent in payloads built
before 0.20.0, where it means unknown and must not be read as production.

It was added after a batch of payloads from a development install had already reached the
collector during testing. Most of that batch predates the field and carries no marker at all,
so for those the install identifier rather than the field is the reliable filter. The specific
identifiers are in the private payload-contract note, not here.

### A wider promise, so a new consent version

> * The Share tab names every plugin publishing its settings, and the consent text is updated to
>   match. Existing sharing settings are unaffected.

Until 0.20.0 the Share tab's exclusion list said "option and setting values", with no exception,
and that was true. It no longer is. `CONSENT_VERSION` therefore goes 1 to 2 and
`PAYLOAD_SCHEMA_MINOR` 2 to 3: a site that agreed to version 1 agreed to a payload with no
third-party settings in it, and `client.consent_version` records which was in force when each
payload was built. Bumping the schema without bumping consent would have been the quiet version
of this change, and the wrong one.

`describe_payload()` now returns `state_components`, and the preview names each contributing
plugin, so "whose settings are in here" is answerable without reading JSON.

### One flaky fetch discarded a page that had been profiled

> * Fixed an analysis reporting itself as incomplete when one page fetch failed after that page
>   had already been profiled successfully.

`SSPA_Archive_Profile::build()` judged each page on `response_code` before looking at its
capture. A page is fetched several times and `response_code` reflects the samples, so a page
whose first sample returned 200 and wrote a full capture, and whose later samples failed, was
treated as a page that had proved nothing.

On this install `admin-new-post` did exactly that on every run - one sample of three failing
with `http_request_failed` at ~600ms - while holding a 14.5 KB capture with its `archives`
section present, 0 archive queries, not truncated. `complete` was therefore false on every full
run, and `sstr_archives_autoconfig_status()` refuses to configure from an incomplete run, so
Super Speedy Archives could not be auto-configured from any run this site would ever produce.
23 of 24 pages, and every archive it needed, were profiled perfectly.

The capture is now the evidence. A page with no decodable capture is still a genuine gap, and so
are a blocked fetch and a 5xx - in the 5xx case WordPress ran far enough to write a capture and
then died, and half a page's queries is not the same answer as a page with no archives.

This is the second bug of this shape in two releases: 0.19.1 fixed `complete` being falsified by
the capture-less `baseline` probe. Both had the same cause, which was inferring "this page
failed" from something other than the page's own capture.

### Tests

- `.tests/cases/37-component-state.php` - new, 35 assertions. Drives the real filter and the
  real exporter: grammar, empty lists, per-key censoring, record isolation under a hostile
  filter, capture timing, the cycle pairing, the disclosure.
- `.tests/cases/20-community-outbox.php` and `22-community-backfill.php` - the deliberate
  hard-coded schema assertions updated from 1.2 to 1.3. They are hard-coded on purpose: a schema
  bump should force a decision, not pass silently.
- Cross-plugin proofs live in the other two repos, since they drive their flows:
  `scalability-pro/.tests/integration/test-apply-good-settings-measures-both.php` and
  `super-speedy-archives/.tests/test-analysis-cycle-submission.php`.

Suite at time of release: 34 case files, 2 pre-existing failures unrelated to this work
(`34-site-characteristics` HPOS row estimate, which fails identically with this work stashed,
and `07-analysis`'s score threshold, which passes when the machine is not under load).

## 0.19.1 (12th August 2026)

Three defects in 0.19.0, all found by Scalability Pro trying to consume the profile, plus the
sharing path 0.19.0 shipped disconnected.

### `complete` was false on every full run

> * Fixed an analysis reporting itself as incomplete on every full run, which told anything
>   consuming the archive profile to disregard it.

The catalogue's first two jobs are instruments, not pages: `baseline` (`/?sspa_baseline=1`,
the server noise floor) and `mail-probe`. `baseline` writes **no capture at all** - the
mu-loader short-circuits it, which is the entire point - so the aggregate saw an undecodable
blob and set `complete = false`, exactly as it would for a page that timed out.

`complete: false` is documented as "insufficient evidence, never nothing needed", so a
consumer following the contract correctly had to refuse the data. Permanently, on every full
run.

It survived testing because the run used to develop the feature was a spot run scoped to
`product-cat,shop`, which filters the probes out. Worked in the narrow case, failed in the
normal one. Case 36 now inserts a capture-less baseline row deliberately and asserts the run
still reports complete.

### WordPress's own archives crowded out the real ones

> * Archive recommendations now only cover archives big enough for an index to be worth
>   building, so WordPress's own one-row template and global-styles queries no longer crowd out
>   your real archives.

WordPress stores editor and theme data as posts - `wp_global_styles`, `wp_template_part`,
`wp_template` - each scoped by the `wp_theme` taxonomy, and queries them on ordinary front-end
requests regardless of whether the site runs a block theme (observed on Astra, where
`wp_is_block_theme()` is false). They are taxonomy-filtered front-end queries that filesort, so
they matched the capture gate exactly.

On a real full run, **18 of 20 qualifying archives were `wp_template_part` or
`wp_global_styles`**; only `product-cat` and `shop` were real.

The fix is a size floor rather than a list of post types to ignore: an index is only worth
building when the archive has 200+ rows, taken as the largest of `found_rows`, `rows_returned`
and the optimiser's `est_rows`. Nothing to keep up to date when WordPress adds its next
internal post type, and a site whose template-part table genuinely grew would be treated like
anything else that size.

This restores the 200-row figure that the first draft of the contract had and that was removed
wholesale when Dave pointed out rows-returned is a poor cost signal. That objection was right,
and the correction over-applied it: rows are a bad measure of **cost** and a good measure of
**whether an index is worth building**. Both bars now apply, and both must pass.

Crucially, everything is still recorded. `archives[]` carries every archive query that ran with
its size, time and plan; only `candidate_composites[]` and `materialise{}` are gated. The
consumer sees the whole picture and chooses. `rows_returned` was added for this: `found_rows`
is `null` whenever `no_found_rows` is set, which is the case on most of WordPress's internal
queries, so there was no size signal for them at all.

### A proposed index carried a taxonomy-table column

> * Fixed a proposed index listing a taxonomy-table column, which belongs to the table the
>   optimisation replaces rather than to the index.

One composite came out as
`(post_type, post_status, taxonomy, topterm_id, term_taxonomy_id, post_date DESC)`.
`other_filters()` scans the WHERE for columns of joined tables and treats them as index-prefix
columns; it picked up `wp_term_relationships.term_taxonomy_id` and filed it as a third table.
It is not a third table - it is the one the mirror table exists to avoid, so the composite
proposed keeping the column the optimisation removes. `term_relationships`, `term_taxonomy` and
`terms` now join `wp_posts` and `wp_postmeta` on the skip list.

### The sharing block now runs

> * Archive shapes are now included when you share an analysis.

0.19.0 put `add_archives()` in `SSPA_Anonymiser::build()`, which has no production callers -
the schema-1 legacy builder for the hub removed in `d1e0b1d`. Moved to
`SSPA_Community_Exporter`, which is what the outbox calls, emitting `sspa/archive-profile@1`
through `add_evidence()` and using the exporter's `page_ref`/`page_class` anonymisation instead
of the raw `page_key` the first cut passed. The dead method has been deleted from the
anonymiser so it cannot mislead again.

The redaction logic itself was correct and moved across unchanged. What was missing was an
assertion that it ran at all: case 36 now builds a real payload through
`SSPA_Community_Exporter::build()` and asserts the evidence is present, is declared in the
evidence manifest, carries no raw page key, and still passes `SSPA_Community_Privacy::validate()`.

### Known, not fixed

On a site already running Super Speedy Archives, the ordering resolves to
`sstr_object_ancestors` columns, because that is genuinely what ran. The profile is honest but
circular for a consumer: Archives reads back its own rewrite. The right answer is probably that
the configuring pass measures with the optimiser off, which is a consumer decision rather than
something this plugin should guess at. Recorded in
`.docs/2026-08-12-archive-profile-remaining-work.md`.

## 0.19.0 (12th August 2026)

The archive query profile: the data contract Super Speedy Archives needs in order to configure
its mirror table from a measured run instead of from a human filling in a settings tab.

### The problem being measured

`wp_posts` is already indexed on `post_date`. The moment a query joins `term_relationships` to
filter by term, that index stops being usable for the sort - the filter and the sort live in
different tables, so MySQL filters and then filesorts. Archives' mirror table earns its keep by
carrying the term columns and the ordering column in ONE composite index:

```
ixDate ON sstr_object_ancestors(post_type, post_status, taxonomy, topterm_id, post_date)
```

Which composites to build is not answerable from the code; it depends on what a given site's
theme and plugins actually order archives by. That is what this release measures.

### Why query vars, and why two capture points

Three of the required fields are absent from the SQL at any length: the stored data type of a
meta key (a CAST says what the query asked for, not what the rows hold), which of several
postmeta joins is the ordering one, and the requested ordering intent.

That last one is the case that would have been missed. WooCommerce applies catalogue ordering
at `posts_clauses`, not in query vars (`WC_Query::order_by_popularity_post_clauses` and
friends), so `orderby=price` becomes `wc_product_meta_lookup.min_price ASC` - a joined third
table that is neither `wp_posts` nor postmeta. Scalability Pro rewrites `ORDER BY` at the same
hook. So `SSPA_Archive_Queries` reads the requested form from `$query->query_vars` at
`the_posts` (genuinely final; any `pre_get_posts` priority is not, because `posts_clauses` runs
after it) and takes the resolved form from the clauses themselves. Both are recorded, because
the two answer different questions.

Ordering is reported as an ordered tuple with per-term `source` (`posts_column` | `postmeta` |
`other_table` | `expression`), direction and cast. The order is the index's column order, and
MySQL 8 serves a mixed `ASC`/`DESC` tuple only from an index declared with matching directions,
so direction is part of the definition rather than a detail.

### Cost attribution is exact, not bracketed

`WP_Query` keeps the statement it ran in `$query->request`, and the profiling wpdb logs every
statement verbatim, so the two are matched by exact string. No bracketing by log position, no
fingerprint heuristics.

### The object cache nearly killed this

Found by the test suite running against WordPress 7.0.3 with a persistent object cache: every
archive record came back with no cost and no plan. WordPress caches `WP_Query` results, so on a
warm run the archive query never reaches the database and never appears in the query log at
all. Matching by fingerprint therefore found nothing, and EXPLAIN - the only evidence that can
establish "unindexed" - was permanently unavailable on exactly the sites this feature is for.

The fix is to retain `$query->request` on the record. It holds the exact SQL whether or not the
query executed, so the plan can still be read, and a query with no matching log entry is
recorded as `cached: true` rather than left as an unexplained null.

### Type inference

`SSPA_Archive_Types` samples the stored values for every meta key an archive orders or filters
on and names a type from Archives' own vocabulary (`varchar`, `bigint`, `decimal`, `float`,
`int`, `datetime`, `date`, `bit`). This is the field only this plugin can supply, and it is the
one that decides whether the optimisation works: an index cannot serve an ORDER BY on a CAST,
which is why the column has to be materialised as a real type, and `_price` declared `varchar`
sorts "100" before "99".

Deliberately conservative - a type is claimed only when every sampled value fits it. `bit` is
checked before `int` because 0/1 also satisfies `int` and a real bit column is smaller and
unambiguous. The sample is spread across the id range rather than taking the first N rows, so a
key whose format changed is not typed off the half that no longer matters. Values that parse as
numbers in some rows and not others are reported `mixed` and never rounded to the majority.
Lookup-table columns take their type from `INFORMATION_SCHEMA` instead, which is exact.

Sampling runs at analysis time only, never inside a profiled request, and is bounded by a
sample size, a chunk count and a whole-pass time budget.

### Selection is by cost examined, never rows returned

Capture is unconditional for qualifying archive queries - it is a read of already-parsed query
vars. Selection happens at analysis time on `ms`, `filesort`, `scan` and `est_rows`. Rows
returned is not a cost signal: the archive this exists to fix scans two million rows in the term
join to return twelve. `found_rows` is recorded as a growth signal and is explicitly barred from
being a reason to skip a query.

### Narrowing versus excluding

`IN` narrows to a term and belongs in the index prefix. `NOT IN` excludes, and Archives serves
it with a `NOT EXISTS` subquery rather than a leading index column. WooCommerce adds a
`product_visibility NOT IN` clause to every product query, so without the split every Woo
composite would have been prefixed on the one taxonomy that never narrows. Caught by reading
real output rather than by review.

### Sharing - written, NOT wired, and the readme says so

> * Archive profiles stay on your own site for now; nothing about them is shared with
>   superspeedy.org in this release.

`profile_blob` is still never submitted, and must not be: it holds SQL with its literals,
absolute server paths, outbound URLs carrying API keys, and every option name the request read.
So an `archives` block was written against the aggregate instead, carrying shapes only - column
names, index shapes, plan verdicts, bucketed row counts.

Meta key names are the one judgement call: they would be the first site-authored strings ever
to leave an install (option names are not shared; they only live in the local capture). A key
matching `SSPA_Rules::known_meta_keys()` identifies software and is shared by name; anything
else identifies a business and is shared as `custom`, keeping its sort direction so the index
shape survives. The list is overlayable from the community feed.

**It was put in the wrong class and does not run.** It went into
`SSPA_Anonymiser::build()`, which has **no production callers** - the only live references to
that class anywhere are `install_uuid()` and `bucket()`. The current payload builder is
`SSPA_Community_Exporter::build()`. `SSPA_Anonymiser::build()` is the schema-1 legacy builder
that `.docs/2026-08-09-community-submission-review.md` section 4 had already flagged as dead
transport; its evidence allowlist was read as though it were the live privacy boundary, and it
is not.

Caught by the `docs-cleanup` pass over the backlog on the same day, before release. The
readme bullet claiming shared analyses could include archive shapes was removed rather than
shipped, because it was untrue as written. The redaction logic itself is correct and is
covered by case 36 - it is simply covered against a method nobody calls, which proves the
logic works but not that it ever runs.

The fix is to add `add_archives()` to `SSPA_Community_Exporter` alongside `add_findings()` /
`add_impacts()`, emitting `sspa/archive-profile@1` through `add_evidence()` with the
exporter's own `page_ref` anonymisation, and to re-point case 36's sharing assertions at it.
Tracked in `.docs/2026-08-12-archive-profile-remaining-work.md`.

### The contract is one document

`.kb/archive-query-profile.md` - "The Archive Query Profile" - is the definitive
specification, field by field, written from the real emitted payload rather than from the
design doc. It is public and published to superspeedyplugins.com, because Super Speedy
Archives and Scalability Pro both build against it.

`docs/agent-api.md` deliberately carries only a pointer to it rather than a second copy of the
shape, and the design doc has been archived. One place to change, nothing to drift.

Consumers should note that
`super-speedy-archives/.docs/2026-08-12-auto-configure-from-analysis.md` was written against
the draft and reads `columns_used[]` and `meta_types{}`; neither field exists. The shipped
equivalents are `materialise.posts_columns[]`, `materialise.postmeta{}` and
`materialise.other_table{}`, plus `candidate_composites[]`, which that doc predates entirely.

### Surfaces

- `SSPA_Report::archive_profile()` and the `sspa/get-archive-profile` ability. Additive, so
  `SSPA_Report::SCHEMA` stays at 1; `SSPA_Archive_Profile::SCHEMA` is its own version.

  contract", never "this site has no archives" - the aggregate counts those separately and
  reports the run incomplete.
- New finding `archive_query_unindexed`, raised from the query plan and never from timing
  alone, with confidence `measured` when a plan was read.

## 0.18.0 (12th August 2026)

Implements `.docs/superspeedy-org-site-cohorts-and-commerce-flows.md` - the client half. The
receiver and superspeedy.org work stays in that repository, as the hand-off asks.

### `sspa/site-snapshot@2`: cohort dimensions instead of one guessed word

**The gap.** The exporter shared an inferred `sector` string, five banded sizes, three version
numbers and an object-cache boolean. That is not enough to build an honest cohort. Order
activity and store scale could not be reconstructed at all; counts for jobs, listings, courses
and events were collected locally and then discarded on the way out; `publisher` meant nothing
more than "over 100 posts"; a WooCommerce site with a magazine attached had to be one or the
other; and the inference carried no version, no confidence and no signals, so the receiver
could never reclassify it later from anything but the plugin list.

**The classifier.** `SSPA_Site_Characteristics::classify()` scores each canonical purpose from
two families of signal: content types mapped through a versioned taxonomy in the rules file (3
points at 100+ items, 2 at 10+, 1 for a handful) and active plugin slugs mapped through the
same taxonomy (2 points each). Highest total is the primary purpose, ties broken on the
taxonomy's own label order; everything else that scored survives as a secondary purpose, capped
at three. Confidence is `high` when the primary purpose has both a stack signal and real content
volume, `medium` on one of the two, `low` otherwise. The result carries `taxonomy_version` and
the coarse signals (`product-content`, `woocommerce-stack`) that produced it, so the receiver
can apply a better classifier later without needing the site to re-measure.

Names are the sharp edge here. A bespoke CPT slug is often the client's own trade name, so a
type outside the taxonomy maps to the content class `other` and never appears as a signal; the
regression test registers a CPT with 200 items - the largest content type on the test site by
some distance - and asserts the slug appears nowhere in the built payload.

**Terminology.** "Site characteristics" is the user-facing idea, "site cohort dimensions" are
the grouping fields. `demographics` is gone from the public contract: these are characteristics
of a website, not of people. `SSPA_Demographics` keeps its name as the local, private collector.

**Sizes.** Posts, pages, primary content items, products, total orders, orders in the last 30
days, users, comments, postmeta, database bytes and active plugin count, each banded through the
existing deterministic ladder and stamped `banding_version: 1`. Null in, null out: an unknown
size stays null rather than banding to `<10`, which would read as "a tiny site" instead of "we
did not measure this".

**Order counts without the hypocrisy.** This plugin's whole argument is that unbounded counts
are what make shops slow, so measuring a shop with one would be an embarrassing way to prove it.
HPOS stores use the information_schema row estimate for the orders table, already fetched for
the size figures. Legacy stores use `wp_count_posts()`, WordPress's own maintained and cached
count - but only below a filterable ceiling of 2,000,000 rows in the posts table; above it the
answer is an honest null with basis `skipped_large_table`. Every route names itself in
`orders_total_basis`.

The 30-day activity figure is a different problem and gets the opposite answer. It was first
written as a capped id fetch, and a cap there is not a safety measure but a silent lie: a shop
doing 40,000 orders a month comes back as the cap and bands as `<10k`, wrong about exactly the
busiest stores in the cohort. It is now a real count of the window through WooCommerce's own
paginated query - HPOS-compatible, and no more expensive, because unlike the all-time total this
one is bounded by its own WHERE clause: 30 days against an indexed date column under both
storage backends (HPOS `type_status_date`/`date_created`, legacy `type_status_date`), so the
database reads the orders in the window and nothing else. Measured on the fixture store at
1.2ms, against 1.8ms for the capped fetch it replaced.

**Environment.** Database family, object-cache and page-cache technology categories (read from
the head of the drop-in file, returning a word from a closed list - never a path or a line of
the file), multisite, locale family, HPOS and checkout type.

**Emitted as a superset, deliberately.** The same array is both the `sspa/site-snapshot`
evidence record and the payload's top-level `site_snapshot`, and the top-level field is read by
receivers that predate this change. Renaming or dropping a v1 key there would break payloads
that are otherwise perfectly readable, so every v1 key keeps its name and meaning and everything
new sits beside it. Payload schema minor 1.1 -> 1.2, additive.

### `sspa/order-management-flow@1`: the shop owner's time stops being discarded

**The gap.** 0.17.0 measured order management - open the order, mark it completed - and the
local waterfall kept it in its own bucket, out of the customer total. `add_checkout()` then
merged only `at_risk`, `secured` and `excluded`, so `flow-view-order` and `flow-complete-order`
were measured on every checkout run and thrown away at the door.

**The record.** Its own evidence type, not more steps on the checkout flow: it measures a
different person's time, and adding it to what a customer waited through would answer no
question anybody has. Carries both steps with their page-profile UUIDs, the management total,
the slowest management step (which is not the run's slowest step - that is usually place-order),
`order_storage`, `checkout_type`, and the status transition canonicalised to WooCommerce's
standard statuses, so a store's own `wc-awaiting-pallet-collection` becomes `other`.

Outcome is honest about what happened: `complete`, `partial` (opened the order but never
completed it), `blocked` (a security layer answered instead of WordPress) or `failed`. A run
whose rows do not prove the steps were attempted - anything from before 0.17.0 - produces no
record at all, because inventing a "skipped" one would tell the receiver that a store was
measured and found to skip management, which is not what happened.

### Checkout segment membership by map, not by structural equality

`add_checkout()` decided each step's segment with `in_array($step, $waterfall['secured'], true)`
- comparing whole step arrays. Place-order contributes TWO rows that share a page key and differ
only in label and timing, so correctness rested on those two rows never being equal, and a
future step that happened to match a harness row would have been silently relabelled. Each
segment is now walked with its own label.

### `status` index on the runs table

> * Added a `status` index to the runs table so the active-run check no longer scans the
>   whole run history, keeping admin pages fast once many analyses have accumulated.

**The symptom.** `SSPA_Run_Controller::active_run_id()` runs
`WHERE status IN ('queued','crawling','analysing') ORDER BY id DESC LIMIT 1` on every admin
page load (overview tab, the runner div) and at the top of every run/preflight. No index led
on `status`: `blog_status (blog_id, status)` cannot serve a status-only predicate, so MySQL
fell back to a reverse PRIMARY scan with early termination. Fine while a run is active (the
newest row matches immediately), but the common case is NO active run, which means scanning
the entire table backwards through rows carrying ~2KB `plugin_set` longtexts. Measured on a
seeded 35k-row copy: 94ms per call. Run rows are never deleted (`ajax_prune_blobs()` only
nulls `profile_blob`), so the table grows monotonically with every analysis, impact
measurement and checkout probe.

**The fix.** `KEY status (status)` on `wp_sspa_runs` - InnoDB secondary indexes carry the PK,
so this is effectively `(status, id)` and the query becomes a covering range scan
(`Using where; Using index`): 94ms to ~0ms on the same 35k-row table. Also covers the
stale-run janitor's `WHERE status IN (...)` sweep. `DB_VERSION` 1.8 -> 1.9; dbDelta adds the
key additively on the first request after update, verified end to end on the dev install.
The sibling `status = 'done' ... ORDER BY id DESC LIMIT 1` lookups were measured fine as-is
(0.4-0.9ms) because recent rows are almost always `done` and the reverse scan stops at once.
Noted for later: `run_uuid_lookup` is fully redundant with `run_uuid_unique`, and
`blog_status`'s `blog_id` is near-vestigial since the tables are per-blog; both are droppable
but need an explicit migration, not worth one on their own.

  `woocommerce_order_status_completed` - which is the saleable number ("marking an order
  completed takes N seconds because plugin X does Y"). The email is intercepted or timed per the
  run's mail mode, because the complete step carries the same `mail` flag the checkout steps do.

The default product is already physical (`default_product` prefers `needs_shipping`), so the
no-payment checkout leaves the order in `processing` and the transition is a genuine
`processing -> completed`; the from/to statuses are recorded in the notes so the panel names the
transition honestly. `update_status('completed')` is a no-op when the order already finished
completed (an all-virtual cart), so that case measures an honest ~0ms rather than sending a
second email.

**The waterfall gains a third bucket.** At-risk (customer can still walk) and secured (money is
in) are the customer's wait; order management is the SHOP OWNER's time, after the sale. It gets
its own `management` / `management_ms` section, kept OUT of the customer total (`total_ms` stays
at-risk + secured), and the panel renders it below the customer figure as "what YOU wait through
handling the order (processing -> completed)". A slow order screen is a real cost, but not one a
customer waits through, and folding it into the checkout total would have been a lie.

Naming: "Analyse checkout flow" -> "Analyse checkout & order flow" on the admin bar and the Pages
tab; the disclosure copy now states the order view and the completion (with its email) before
anything runs; the `run-checkout-flow` ability description says the same. `run_type` stays
`checkout` in the database - the rename is a label, exactly as with the deep -> plugin-impact
rename.

**Cache gotcha found by test:** the transition happens in the loopback, a different process, so
the flow's own order cache is stale when it reads the resulting status - `wp_cache_delete($id,
'orders')` + `clean_post_cache($id)` before the re-read, or a completed order reads back as
processing.

Case 33 drives the real `start(['type' => 'checkout'])` path and asserts: both steps measured
and the view step ran as admin and actually rendered (~2s order screen on the test box); a
fixture hooking `woocommerce_order_status_completed` fired during the run (proof the cascade ran
inside the measured step, in another process); processing -> completed recorded; the waterfall's
management bucket holds both steps with real time while the customer total excludes them; and the
completed order is still deleted afterwards.

**Two test-harness gotchas this surfaced.** (1) The waterfall's `complete_from_status` /
`complete_to_status` read from the flow notes, which `finish_checkout` nests under `flow` - the
first cut read the top level and the panel label came back empty; case 33 now asserts the
waterfall's own status fields, not just the raw notes. (2) Case 19's mail-observer fixture writes
its log from inside the loopback requests, while the controller process had `delete_option`'d the
log key before the run - putting it in that process's `notoptions` cache. The new completed-order
email (written from a management loopback after the delete) was genuinely in the DB, but the
controller's `get_option` returned the stale empty default; the raw DB row was correct. Busting
both the value cache AND the `notoptions` array before the cross-process read is the fix. A long
diagnosis that turned out to be zero product change - the classic checkout still sends its order
emails, and now a completed-order email besides.

## 0.16.1 (11th August 2026)

### The measurement timeout is a setting

> * New Settings tab with the measurement timeout: how long each measurement request may wait
>   for a page before giving up (10-900 seconds, default 60).

**The symptom.** On a large site with real performance problems, Dave raised the server
timeouts to 600s, loaded the problem page in his browser, then ran "Analyse this page" - and it
recorded nothing, while Query Monitor (which records in-process during the page load itself)
captured it fine.

**The cause.** Both crawler send paths hardcoded `'timeout' => 60` on the loopback requests.
Every sample of a multi-minute page was abandoned at 60 seconds; the raised server limits never
entered into it. The perverse part: the slower the page, the more its owner needs the
measurement, and the more certainly the hardcoded ceiling discarded it.

**The fix.** `loopback_timeout` in `sspa_options`, surfaced on a new Settings tab (saved in
place, no reload, clamped value echoed back into the field). `SSPA_Crawler::loopback_timeout()`
feeds both send paths, and the sanitiser (10-900, non-numeric falls back to 60) is shared with
the save handler so the stored value and the used value cannot disagree. The tab's copy carries
the operational caveats: the server/proxy timeouts you raised for your browser must cover this
number too, and PHP's `max_execution_time` should comfortably exceed four times it, because one
background worker makes the warm-up and three samples back to back.

Case 32 proves it with a page that really sleeps 12s: at a 10s timeout nothing is measured and
the samples record the abandonment; at 30s the same page measures at 12,185ms. Two gotchas the
case encodes: the sanitiser's floor is 10 (asserting a set value of 5 sticks fails correctly),
and the probe query arg must not be `sspa_`-prefixed or the catalogue matcher strips it and the
run measures plain `home` without the sleep.

This is the containable half of the browser-transport discussion (see the 0.16.0 conversation):
a timeout raised to cover the page still leaves the admin-ajax worker and any front proxy as the
next ceilings. The full fix - the admin's own browser making the profiled requests, so the
budget is by construction whatever just loaded the page by hand - remains designed but unbuilt.

## 0.16.0 (10th August 2026)

Dave's framing, verbatim from the design conversation: "unless you can 100% guarantee that your
guards will work... the plugin is meant to be ZERO SERVER IMPACT." No guard stack can promise
100% - a plugin can react to an absence in ways no interception reaches (its own mysqli
connection, filesystem writes, an outbound licence call). So this release does two different
things at once: it moves the DECISION to the person who knows their plugins (consent), and it
closes every reaction route we can actually reach (guards), with the residual stated plainly
rather than waved away.

### Nothing is measured until the site owner picks it

> * Plugin Impact Analysis now always starts from a chooser: nothing is measured until you pick
>   the plugins yourself, nothing is preselected, and the chooser explains exactly what will
>   happen and what it will cost before anything runs.

The "Run Plugin Impact Analysis" button used to start a sweep of every eligible plugin on one
press. On a client site with plugins whose deactivation behaviour nobody has audited, that is
too easy a button - Dave's words - for what it can set in motion. It now opens the same picker
the page panel uses, site-scoped: the eligible plugins ordered by attributed cost, dependency
groups shown against each ("measured together with X, which cannot run without it"), the
caution stated, a live estimate in measurements and minutes, and NOTHING ticked. The page
panel's picker loses its pre-ticked "blamed" defaults for the same reason - "Select blamed"
remains as a one-click helper, but the act of selection is always the user's.

Choosing every plugin still runs the classic two-phase screened sweep (theme swap included), so
the whole-site measurement is exactly as cheap as before - it is just chosen rather than
default. A shortlist runs targeted. The cache modes are opt-in from the chooser in both scopes,
where they used to be automatic on site sweeps. `wp sspa run --type=deep` is unchanged: a typed
command with `--suspects` is already explicit consent.

### Reactions are silenced, refused, caught, and learned from

> * If a plugin reacts to another being excluded during a measurement, its activation and
>   deactivation routines are now silenced before they can run, and destructive database
>   statements are refused for that request.

The 0.14.0 write guard only stopped the plugin list changing; core fires a plugin's OWN
(de)activation routines before the write it guards, and scalability-pro's deactivation hook -
`spro_deactivation_drop_indexes()` - drops database indexes. Deactivation is not where
destructive cleanup belongs (that is `register_uninstall_hook`, which runs on delete), but the
sweep cannot rely on every vendor's discipline.

Three layers, each doing what the previous cannot:

**Hook silencing (mu-loader).** Core fires `deactivate_plugin` before `deactivate_{$file}` and
`deactivated_plugin` (activation mirrors it), all inside the same `!$silent` guard. A catcher
at `PHP_INT_MIN` on the first action records the attempt with a backtrace, then
`remove_all_actions()` on the plugin's own hook AND the general observer hooks - so a security
plugin's audit log cannot record a deactivation that never happened - then re-arms itself for a
second attempt in the same request. The reactor's routine never runs. WP-Hook iterates a
priority snapshot but reads callbacks live, so removing not-yet-reached listeners mid-fire
works; the mu-loader's own frames are filtered out of the recorded backtrace or attribution
lands on `mu:sspa-loader` instead of the reactor (found by test, not by review).

**Statement refusal (profiling wpdb).** Hook silencing cannot reach a reaction coded INLINE -
"dependency missing, drop my indexes" straight in the bootstrap, or TGMPA-style library code
the main-file scan never reads. So during isolation cells (`ps`-flagged requests; the db.php
shim sets `sspa_isolation_cell`), `SSPA_Profiling_WPDB::query()` classifies and refuses
destructive statements before execution: DROP TABLE/INDEX/VIEW/TRIGGER/DATABASE, TRUNCATE,
RENAME TABLE, ALTER TABLE carrying a DROP, and whole-table DELETE. Deliberately NOT all writes
- pages legitimately write transients, sessions and carts, and a bounded DELETE is routine
cleanup - and DROP TEMPORARY TABLE stays allowed. The caller is told the statement succeeded so
it does not retry or error-cascade. This is why the sweep now REQUIRES our drop-in
(`build_sweep_jobs` refuses otherwise, naming the swap option): degraded mode has no seat
between a reaction and the database. An aborted start now also restores a held foreign drop-in,
which it previously leaked.

**Catch -> report -> learn.** Reactions recorded by either layer are attributed (the backtrace
names the REACTOR, not the target - Rank Math Pro reacting calls `activate_plugin()` on Rank
Math), carried through the capture into the profile's sample summaries, and at `finish_sweep`:
the cell is marked unresolved rather than trusted (an excluded-plugin cell in which the
dependant partially re-established itself is not a measurement); a `isolation_reaction` finding
is written naming the reactor, the excluded plugin, the reaction kinds and the refused SQL -
findings ride every shared payload, so this is the "catch it into superspeedy.org" half, with
the privacy allowlist passing the shape and a fingerprint, never raw SQL; and the pair lands in
`sspa_learned_groups`, which `must_exclude_together()` merges ahead of the code scan. The next
sweep excludes the pair together, so a given reaction can happen at most once per site - fully
neutralised even that once.

### What this still does not guarantee

Stated here because the guards must never be oversold: a reaction through a plugin's own
mysqli/PDO connection, filesystem deletion, or an outbound HTTP call (a licence seat release)
is outside all three layers. That residual is why the chooser leads with "choose plugins you
understand" and nothing is preselected. The community angle - superspeedy.org aggregating
`isolation_reaction` findings into a served `dependency_families` feed so site N+1 never
provokes what site 1 caught - is server-side work in the superspeedy.org repo; the client half
(the finding in the payload) ships now.

### Proven able to fail (case 31)

The fixture is scalability-pro's shape: a deactivation hook that drops a real index on
`wp_options`, an INLINE index drop, and a runtime-assembled dependency path the scanner cannot
see. The case first runs both destructive paths with the guards disarmed - the hook really
drops the index, the same ALTER really executes through the shim with the guard off - so a pass
is a pass because the guards worked, not because the fixture was harmless. Then the e2e sweep:
orphaned 4 times, routine never ran, index intact, both plugins active, finding + notes +
learned group written, and a second sweep that groups the pair, provokes nothing, and finally
produces a verdict with `group_members` recording who it covers.

One harness gotcha for the file: `wp eval-file` textually replaces `__FILE__` before eval'ing,
so a fixture written via heredoc must never use it - it silently becomes the CASE file's path
and a `register_deactivation_hook(__FILE__, ...)` registers under a name that can never fire,
making the guard assertions vacuous. Case 31 carries the warning inline.

## 0.15.0 (10th August 2026)

The other half of the 0.14.0 fix. That one stopped a measurement changing which plugins the
site runs. This one stops us provoking the situation at all - and, as a side effect, makes a
whole class of plugin measurable for the first time.

### Plugins that cannot run without each other are measured together

> * Plugin Impact Analysis now reads each plugin's own code to find which plugins cannot run
>   without another one, and measures those together in one go, so nothing is ever left running
>   without something it depends on.

**Why the write guard is not enough.** `deactivate_plugins()` fires `deactivate_plugin`,
`deactivate_{$plugin}` and `deactivated_plugin` *before* the option write that 0.14.0
neutralises, so a plugin that switches itself off still runs its own deactivation routine
inside the measurement. Rank Math Pro's happens to be `private function deactivate() {}`, so
nothing came of it there; the next plugin's might unschedule cron, flush rewrite rules or call
a licence server. Worse, Rank Math Pro does not only deactivate itself - it calls
`activate_plugin()` on the free version first, and an activation hook is a whole installer
(options, capabilities, cron). Measured against the real thing: the case-29 fixture, orphaned
across one warm-up and three samples, ran that path **four times in a single cell**.

**Why the declared header could not fix it.** `SSPA_Dependency_Map::required_by()` has always
read core's `Requires Plugins`. On the site this was found on, all nine active plugins declare
nothing at all and the map is empty - which is precisely why Rank Math was a candidate. A
grouping rule driven by that header alone would have changed nothing.

**What the code says instead.** Rank Math Pro carries everything needed as literals in its main
file:

```php
private $free_version_plugin_path = 'seo-by-rank-math/rank-math.php';   // rank-math-pro.php:107
...
if ( ! $this->is_free_version_activated() ) {          // reads get_option('active_plugins')
    if ( ! $this->activate_free_version() ) { ... }    // → activate_plugin()
}
add_action( 'admin_init', [ $this, 'auto_deactivate' ] );   // → deactivate_plugins( self )
```

So `SSPA_Dependency_Map::code_signals()` scans each active plugin's **main file only** - the
requirement check has to run before anything else, so it lives in the bootstrap - for three
things: literal `dir/file.php` strings naming another *active* plugin, a `deactivate_plugins(`
call, and an `activate_plugin(` call. Nine file reads, cached against the mtime+size of every
active main file. On the site in question it produced exactly one edge:

```
seo-by-rank-math-pro   self-deactivates=YES  activates-others=YES  names=[seo-by-rank-math/rank-math.php]
```

An edge needs BOTH halves: naming another plugin, and being able to activate or deactivate
something. A compat shim mentions plugins it will never act on, and the capability alone says
nothing about which plugin it would react to. Declared `Requires Plugins` headers still count on
their own. `must_exclude_together()` then takes the transitive closure, so excluding A pulls in
B and anything that cannot run without B.

`build_sweep_jobs()` puts the whole group in one isolation payload, so the dependant never loads
to discover anything is missing. It is also the better measurement: nobody runs Rank Math Pro
without Rank Math, so the cost of the pair is the cost of having it.

**Dependency roots are measurable again.** `isolation_candidates()` used to drop any plugin
another one required, which kept it safe and made it permanently unmeasurable - on a Rank Math
site the SEO plugin, usually one of the most expensive things on the page, could never get a
measured verdict. It is a candidate again now that excluding it can never orphan anything.

**Saying so.** `plugin_impacts` gains `group_members` (DB_VERSION 1.8). The Plugins tab prints
"measured together with seo-by-rank-math-pro, which cannot run without it", the page panel says
"with X, which cannot run without it", the running feed reads "home with seo-by-rank-math +
seo-by-rank-math-pro disabled", and the panel's plugin picker says which plugins travel together
*before* the run starts. A delta credited to one plugin when it belongs to two would overstate
that plugin and hide that removing one means removing the other.

### Grouping must not become a way round the fragile list

Found while reviewing the above, before it could bite. Security plugins are on a fragile list
and are never excluded - but a group is excluded wholesale, so if something a fragile plugin
depends on were still a candidate, its group would take the security plugin out with it for
the test requests. `isolation_candidates()` now drops any plugin whose group touches the
fragile list. Better to leave one plugin unmeasured than to measure a page with the site's
security plugin missing. Case 30 covers it with a fixture using the `wordfence` slug, which is
on the bundled security list.

### Case 09's fixture was overdue the fix case 07 already had

Not part of this feature, but it failed the suite while verifying it, so it is fixed here.
Case 09 plants a "bad plugin" whose third sin is `SELECT p1.ID FROM posts p1, posts p2, posts
p3 ORDER BY rand()`. Case 07 bounded every alias to `(SELECT ID FROM posts LIMIT 120)` after
hitting this exact problem; case 09's copy was never updated. `run-tests.sh` reseeds the
WooCommerce sample data whenever the product count drops, so the posts table accumulates: at
464 posts the unbounded join is 99.9 MILLION row combinations and the home page took **82
seconds** to render (0.10s with the fixture removed). The source spot run then blew its 180s
deadline and the sweep never started, which presents as "deep run done: crawling" and four
cascading failures - a fixture problem wearing a run-controller costume. Bounded, the same
fixture measures ~800ms and the case passes in every cache mode.

### The two cases are deliberately complementary

`.tests/cases/30-dependency-groups.php` plants a Rank Math Pro shaped pair - dependency named as
a literal, `activate_plugin()` and `deactivate_plugins()` in the main file, each fixture counting
its own orphaning. With grouping the count is 0; with `must_exclude_together()` stubbed to
`array()` it is 4, the verdict's `group_members` is NULL and the feed line names one plugin.

That change would have quietly hollowed out case 29, whose fixture also named its dependency as
a literal: grouping would have covered it, so it would have passed without the guard ever being
asked to do anything. Its fixture now assembles the path at run time - the dependency a scanner
cannot see, which is exactly the residual the guard exists for - and the case asserts both that
grouping does NOT cover the pair and that the dependant really did try to deactivate itself
(4 times) before asserting the plugin list is unchanged.

## 0.14.0 (10th August 2026)

Implements `.docs/2026-08-10-page-analysis-unification.md` sections 1-3 (section 5, the Plugin
Impact Analysis rename, went out in 0.13.1; section 4, flows, is deliberately deferred). And
fixes a defect the new one-click page sweep made trivially easy to hit, found by running that
sweep against a real site rather than by reading the code.

### A measurement deactivated two plugins for real

> * Fixed a plugin that switches itself off when a dependency is missing staying off after a
>   Plugin Impact Analysis measured it: a measurement can no longer change which plugins your
>   site runs.

**The symptom.** On the dev site on 10th August 2026, a page-scoped sweep of `admin-plugins`
finished normally and produced good verdicts for all seven plugins. Rank Math and Rank Math Pro
were then inactive - not for the measurement, for everyone - and this plugin's own admin notice
was offering a spot check for "you just deactivated seo-by-rank-math-pro", a thing nobody had
done.

**The cause.** Isolation has always been a read filter: `option_active_plugins` is filtered for
the profiled request only, so the excluded plugin's code never loads, and we fire no
activation or deactivation hooks. The mu-loader's comment said as much. What it missed is that
the plugin being measured gets a vote. Rank Math Pro, finding Rank Math absent from
`active_plugins`, did the responsible thing and called `deactivate_plugins()` on itself - which
reads the FILTERED list, removes itself from it, and writes the result to the real option. One
`update_option` and the site is running two fewer plugins than it was, permanently, with the
exclusion we only ever meant to last one request now baked in.

Any plugin with a hard runtime dependency it checks this way can do it. The sweep has been able
to trigger it since 0.8.0; what changed in 0.14.0 is that "measure the plugins on this page" is
now one click from the panel, on whatever page you happen to be looking at, including a wp-admin
screen where `deactivate_plugins()` is already loaded.

**The fix.** While the isolation filter is armed, no write to the plugin lists may persist. The
mu-loader captures the true stored `active_plugins` BEFORE adding any filter of its own, then
registers `pre_update_option_active_plugins` (and the network equivalent) returning that
captured value at `PHP_INT_MAX`. `update_option` applies the filter before its equality check,
so whatever a plugin believes it is writing, the stored content is what was already there. The
deactivation hooks still fire inside the measurement - we cannot stop a plugin calling a
function - but nothing about it outlives the request.

Second half of the same fix: the mu-loader now defines `SSPA_PROFILED_REQUEST`, and
`SSPA_Admin_Page::register_toggle_prompt()` ignores toggles seen during a profiled request. That
is what stops the "you just deactivated X - want a spot check?" prompt appearing for a
deactivation that never happened.

`.tests/cases/29-isolation-writes.php` is that site reduced to two fixtures: a dependency, and a
dependant that calls `deactivate_plugins()` on itself when the dependency is missing. With the
guard removed the case fails with the active plugin list shrunk from 6 to 4 - both fixtures gone,
which is exactly the Rank Math outcome, because the persisted write is the filtered list.

### One profile view, not two

> * "Analyse this page" and clicking a page on the Pages tab now open the same panel, carrying
>   everything either of them used to show on its own.

**The symptom.** `SSPA_Adhoc::ajax_result()` returned a bespoke JSON shape that `sspa-adhoc.js`
turned into the branded popover: top 5 slow queries, boot phases, Excimer, Cloudflare state. The
Pages tab's row click called `sspa_page_detail` and built different markup in `sspa-admin.js`
with `html +=`: components, 10 slow queries with callers, HTTP calls, hook callbacks. Same
stored capture underneath, two presentations, each missing something the other had.

**The cause.** Nobody decided they should differ. Two renderers over one dataset drift by
default - every column added to one is a column the other silently lacks.

**The fix.** `SSPA_Profile_Panel::render($profile_id)` is now the only renderer, a PHP partial
returning the panel body. `ajax_result()` became what it should always have been: a resolver
from URL to newest `profile_id` for that page, which then calls the same renderer the Pages tab
calls through `sspa_profile_panel`. The 100 lines of `html +=` in `sspa-admin.js` are gone, and
the row click is three lines calling `window.sspaPanel.openProfile(id)`. `sspa_page_detail` is
deleted.

Rendering server-side also made the additions cheap, so the panel now carries the union plus
what neither had: per-component attribution in BOTH modes (both tables emitted up front and
swapped client-side, since caller mode is recomputed from the capture already in hand -
`SSPA_Attribution::caller_aggregate()` exposes that for one capture), the outbound HTTP calls
with their calling function, an `EXPLAIN` note under each slow query, the page's object cache hit
rate and autoloaded-options size, and the measured plugin impact for that page.

The doc's consequence, taken deliberately: the "Open in Performance Analysis" link is gone. With
one panel there is nothing extra to go and see.

Presentation follows the popover everywhere, so the Pages tab now opens the branded floating
panel rather than an inline table row. Its CSS and JS were already enqueued on every admin
screen; `SSPA_Adhoc::enqueue()` now also fires when the admin bar is hidden but we are on the
plugin's own page, or hiding the bar in wp-admin would have taken the drill-down with it.

### Plugin impact, scoped to the page you are looking at

> * New "Measure plugin impact on this page" on the panel: tick the plugins, read "7 plugins x 1
>   page = 9 measurements, about 20 seconds" before anything starts, and the verdicts appear in
>   the same panel when it finishes.

Plugin impact was a whole-site sweep, when the question is nearly always about one page - and
since 0.12.7 `build_sweep_jobs()` honours `page_keys`, so one page costs `6 x plugins` rather
than `6 x plugins x 36 pages`. The panel now offers it where the question gets asked.

`sspa_impact_plan` returns the eligible plugins with what this page's own attribution charges
each of them - SQL + HTTP from the capture's components, plus the PHP the boot timer charged,
because a plugin can cost 200ms of hook time without running a query. Anything with a cost is
ticked by default; the rest are listed unticked, with "select every eligible plugin" for the
full sweep.

The estimate is the point of the box. The 72 -> 216 surprise was a missing estimate, not a wrong
number, so the JS mirrors `sweep_block_jobs()` - one baseline per cache mode opens the block and
another every `SWEEP_REBASELINE_EVERY` cells - and multiplies by seconds-per-measurement learned
from the median of this site's last five completed runs (`SSPA_Profile_Panel::seconds_per_job()`),
not a constant. Two assertions in case 28 pin the formula against the real planner: one plugin on
one page queues 2 measurements, two plugins queue 3. Where the object cache can be toggled, the
cache modes are an explicit tick-box quoting their own ceiling, and declining them sets
`cache_modes => false`, which stops `sweep_extend_phase2()` adding them.

**Sweeping a page no analysis has profiled.** `build_sweep_jobs()` refused any page the last
baseline/spot run did not cover, which would have made the button dead on exactly the pages
ad-hoc profiling is used for - a particular product, an order edit screen. It now accepts a
`url` argument, resolves it through `SSPA_Adhoc::job_for()` and sweeps that one page, requiring
no source run at all: the deltas were never computed against the source run, only against the
baselines the sweep takes for itself at each page block. A URL-scoped run is targeted by
construction (one page - screening it at two samples and then confirming the same cell would
only add measurements), and its `plugin_impacts.baseline_run_id` is null rather than 0.

`wp sspa run --type=deep --url=... --no-cache-modes` and the `url`, `pages` and `cache_modes`
inputs on the `run-deep-analysis` ability expose the same thing to the CLI and to agents.

### Ad-hoc results merge into the Pages tab

> * The Pages tab now lists the newest measurement of each page, whether it came from a full
>   analysis or from analysing that page on its own, with the date it was taken; the site score
>   still comes only from full analyses.

Open question 1 from the doc, answered. Since 0.13.0 an ad-hoc run of a catalogue page files

## 0.13.1 (10th August 2026)

Closes the remaining findings from `.docs/2026-08-09-community-submission-review.md` (3.3, 3.4,
3.5, 3.6, 3.8), renames Deep Analysis, and bounds the test fixture that cost hours on 9th August.

### Sharing can no longer fail silently (3.6)

Only exporter errors reached `sspa_submission_build_errors`; encode, compress and size-limit
failures returned a `WP_Error` recorded nowhere, and the Share tab rendered that list only for
the backfill path. So a site could have sharing on and send nothing indefinitely with no sign
anywhere - which is exactly what happened on superspeedyplugins.com for six runs. All four paths
now record, and the Share tab carries a warning when sharing is on and anything failed to
prepare, with the technical detail behind a disclosure rather than in the user's face.

### A queued payload no longer needs its run (3.4)

`Client::submit()` read `run_type` from the runs table purely to build the manifest, so a deleted
run would strand its payload - contradicting the "immutable bytes survive anything" promise.
`run_type` is now stored on the outbox row (DB_VERSION 1.7). Rows written before this keep the
old path as a fallback.

### A wrong collector address stops killing the queue (3.5)

Anything outside {408, 425, 429, 500, 502, 503, 504} was permanent, so a 404 from a mistyped
`sspa_collector_url` moved every queued item to `permanent_failure` on its first attempt, and
correcting the typo meant pressing Retry now once per row. A "permanent" status now gets
`PERMANENT_GRACE` (3) attempts first; a genuinely permanent error simply fails again and lands
there anyway.

### A manual share stops getting stranded (3.3)

`run()` deleted `sspa_share_manual_pending` whenever nothing was *currently due* - including when
a manually shared item was inside its retry backoff. With site-wide sharing off, `maybe_nudge()`
could then no longer re-arm, leaving the item dependent on a single scheduled event.
`has_pending_manual()` asks the question that was actually meant: is any manual row still in a
non-terminal state.

### Schema upgrades run one at a time (3.8)

`maybe_upgrade()` fires from `plugins_loaded` on whichever request arrives first after an update,
and ran `dbDelta` plus `ensure_run_uuids()`'s `ALTER TABLE ... ADD UNIQUE` with no lock, so two
concurrent requests could race the DDL into a duplicate-key-name error. Now behind an
`add_option` lock that expires after 300s so a fatal cannot wedge the upgrade permanently.

### Deep Analysis is now Plugin Impact Analysis

Labels only, across the Overview, Plugins tab, Share tab, History, the runner title and the
ability description. `run_type` stays `'deep'` in the database: changing it would break every
historical row and the `run_type` field of every community payload already archived.

### The progress count says which phase it is in

`Phase 1/2, screening - 48 / 72 measurements`. The phase was only ever in the panel title, so a
total jumping from 72 to 216 part-way through read as a bug rather than as phase 2 adding the
cache-off and priming measurements.

### The test fixture stopped depending on how much data the container held

`07-analysis.php` plants a deliberately slow query - three unbounded joins over `wp_posts` with
`ORDER BY rand()`, tuned in its own comment to ~800ms. Its cost is O(posts^3). Once the container
accumulated 440 posts it reached ~170 million rows, every profiled request hit the 60-second
crawler timeout, and eight assertions failed presenting as "the analysis engine found nothing".
Each alias is now bounded to 120 rows, so the query stays slow on purpose and stable in cost.

## 0.13.0 (10th August 2026)

### Consent you can actually inspect

> * New "See exactly what gets sent" button on the Share tab.

The preview always existed, but only for an ALREADY QUEUED payload - so the order was opt in,
queue, then look at what you agreed to, which is backwards for a consent decision.
`SSPA_Submitter::dry_run_preview()` builds the payload for the newest shareable run and returns
it without storing, queueing or sending anything (asserted: outbox count unchanged either side).

`describe_payload()` renders it in plain English above the JSON, because a JSON blob only
reassures people who read JSON, and they are not the people a privacy promise has to convince.
The download is built client-side from the payload already on screen, so the file is
byte-identical to what was shown rather than a second server render.

### The queue stopped depending on WP-Cron

> * Queued submissions are now delivered by your browser while you are on the analysis screen.

WP-Cron only fires on traffic and plenty of hosts disable it in favour of a real crontab, so a
queue that relies on it can sit for days. `sspa_submission_tick` drains it from the browser,
chaining while more is due and firing immediately after anything is queued. Cron stays as the
backstop for headless sites and WP-CLI runs. No new locking: the compare-and-set claim in
`begin_attempt()` and the receiver's `submission_uuid` idempotency already cover duplicates.

### Measured impact stopped reporting a number nobody experiences

> * Measured impact now reads "adds 120ms typically, up to 340ms on wc-checkout".

The headline summed `delta_ttfb_ms` across every page. No visitor loads every page type at once,
so the total was meaningless - and it scaled with how many pages you happened to measure, so a
wider sweep made a plugin look worse. Now: median across affected pages (median, not mean -
deltas are skewed and one pathological page should not define "typical"), the worst page named,
and coverage stated. The worst page was already computed; it was demoted to small grey text while
the meaningless sum got the bold treatment.

### Impact is kept per page, not per sweep

> * Measured impact is now kept per page.

Selection was `MAX(test_run_id)` per plugin - every row from that plugin's latest sweep. Once
sweeps can be scoped to one page (0.12.7), that throws away every page the scoped sweep did not
touch, and a plugin measured on one page appears to affect only that page. `latest_impacts_sql()`
now takes `MAX(id)` grouped by plugin, page and cache mode, so a targeted re-measure updates
exactly what it measured. `MAX(id)` rather than `MAX(created)`: two sweeps can share a second.

### An analysed page files under the page it is

> * Analysing a page that the full analysis already covers now files it under that page.

`SSPA_Adhoc::job_for()` derived `url-<md5>` for everything, so analysing the shop page from the
admin bar produced a result that sat beside the same page measured by a full analysis and was
comparable with nothing. It now matches the URL against `SSPA_Catalogue::build()` and reuses that
job's page key and variant. Comparison normalises trailing slashes, our own `sspa_*` arguments and
query order; an unknown URL still gets its opaque key, which is what keeps URLs out of submissions.

Design for the remaining page work - one unified profile panel, plugin impact scoped to a single
page, and flows as a category (checkout, edit product, edit order) - is in
`.docs/2026-08-10-page-analysis-unification.md`.

## 0.12.0 (9th August 2026)

The full specification, the wire contract and the delivery checklist are in
`.docs/performance-analysis-submission-implementation.md`. The matching receiver side lives in
the separate `superspeedy.org` repository. This section records what changed in the plugin and
why; it does not repeat the specification.

### Measured plugin versions are recorded and shown

> * New Version column on the Plugins tab, showing the version each component was at when the
>   analysis measured it.

> * Deep Analysis records the plugin version it measured, and the Plugins tab now says when a
>   measured verdict was taken against a version you no longer run.

> * The per-page breakdown names the version its measurements came from.

> * The History tab lists the components and versions each analysis measured.

**What it was.** The measurement-time inventory was already captured: `SSPA_Run_Controller::start()`
writes `{type, slug, version}` for every active plugin plus the theme into `runs.plugin_set`, and
the community exporter has been sending it as `component_version` on five evidence types since the
schema-1.1 work. Locally none of it was reachable. No table had a version column, and no screen
rendered one, so the plugin that produced the numbers could only be named by slug.

That mattered most on the Plugins tab, where two different runs share one row. Attribution totals
come from the latest baseline or spot run; Measured impact comes from each plugin's own most recent
deep sweep, which can be weeks older. A customer reading "adds 340ms" had no way to tell the verdict
was measured against a release they had since updated past. `plugin_set_hash` is `md5(active_plugins)`
and ignores versions, so a plugin update produces an identical hash and nothing else flagged it
either.

**What it is.** `sspa_plugin_impacts` gained a `plugin_version varchar(32) NULL` column (DB_VERSION
1.5 to 1.6, additive, handled by the existing `dbDelta` in `SSPA_Schema::create_tables()`), and
`SSPA_Run_Controller::finish_sweep()` stamps every impact row with the version the deep run itself
recorded. The value is resolved through two new methods on the run controller:

- `decode_component_versions($plugin_set)` turns a `runs.plugin_set` value into a
  `"type:lowercased-slug" => version|null` map;
- `component_versions($run_id)` is the query-backed form, statically cached per run;
- `component_version($run_id, $component, $type)` looks up one component.

Both read the run's own snapshot and never `get_plugins()`, so a plugin updated after the
measurement cannot relabel what was measured. `.tests/cases/09-deep-e2e.php` proves that
directly: the bad-plugin fixture now carries `Version: 2.4.1`, the deep sweep must stamp `2.4.1`
on every impact row, and the case then rewrites the fixture's header to `9.9.9` and asserts the
live inventory reports `9.9.9` while the stored impact still reports `2.4.1`.

Runs recorded before 0.12 stored a bare file list with no versions. Those stay null and render as
`-` or "version unknown"; the alternative - filling in whatever is installed today - would be
worse than an admitted gap, and is the same rule the exporter already applies to historical
inventory.

On the surface: `includes/admin/tabs/plugins.php` gains a Version column sourced from the
displayed run, plus a `sspa-impact-stale` note under Measured impact when the impact row's
version differs from it. `ajax_plugin_detail()` returns `measured_version` and the drill-down
heading names it. `includes/admin/tabs/history.php` decodes `plugin_set` from the run row it has
already selected - `decode_component_versions()` exists so that column costs no extra queries -
and lists each run's components in a collapsed `<details>`.

### The plugin title moved into the tab row

> * The page title now sits at the start of the tab row, with the running plugin version beside
>   it.

`SSPA_Admin_Page::show()` had a plain `<h1>` above the tab bar. The title and version now sit
inside the `nav-tab-wrapper` as a `.sspa-brand` span with a `.sspa-ver-chip` pill carrying
`SSPA_VERSION`, matching the header treatment in Super Speedy AJAX Prices. The `<h1>` is retained
as `screen-reader-text` because WordPress moves admin notices to just after the first heading and
screen readers expect a page title; dropping it entirely would misplace every notice on the
screen. The wrapper is `display: flex` with `align-items: flex-end` so the tabs stay seated on
its bottom border.

### The rules feed stopped retrying a dead endpoint every hour

> * The community rules feed backs off for 12 hours after a failed fetch instead of retrying
>   every hour.

**The symptom.** Every install ran an outbound `GET https://superspeedy.org/?rest_route=/ssph/v1/rules`
with a 30-second timeout once an hour, forever, and threw the result away. Confirmed against the
live host on 9th August 2026: the route returns `{"code":"rest_no_route",...,"status":404}`.

**The cause.** `SSPA_Rules_Feed::refresh()` only wrote its `sspa_rules_feed` transient on success,
and `SSPA_Run_Controller::cleanup()` - on the hourly `sspa_cleanup_event` - called `refresh()`
whenever that transient was absent. A feed that never succeeds therefore has no cache to gate the
next attempt, so "daily-ish" was in practice hourly. The route itself was removed with the rest of
the schema-1 hub in `d1e0b1d`; the rules feed is the one consumer of `SSPA_Submitter::endpoint()`
that survived, and superspeedy.org has never published a replacement.

**The fix.** A separate `sspa_rules_feed_backoff` transient, set for 12 hours by
`SSPA_Rules_Feed::back_off()` on every failure path (transport error, malformed body, signature
failure) and deleted on success. `refresh()` returns `sspa_feed_backoff` without making a request
while it is set, which caps a dead feed at two attempts a day instead of twenty-four. The caller
now also only calls `SSPA_Rules::flush()` when `refresh()` actually returned `true`, so a failed
fetch cannot discard the merged rules already in memory.

This is a containment fix, not a resolution: the feed still has no live source. Publishing the
signed feed, or retiring `SSPA_Submitter::hub_url()`/`endpoint()` and the dead
`SSPA_Anonymiser::build()` along with it, is outstanding.

### A running analysis shows what it is measuring

> * A running analysis now opens in the middle of the screen and lists every measurement as it
>   is taken, e.g. "home with super-speedy-search disabled, object cache off", instead of only a
>   progress bar.

> * Fixed the minimise button on the running-analysis panel doing nothing.

**Why a bar was not enough.** Clicking Measure on one plugin produced "134 / 216 measurements",
having started at 72 and grown. All three numbers are correct and none of them is explicable from
a progress bar. A targeted run skips screening and goes straight to every page
(`$phase1_pages[$slug] = array_keys($page_jobs)`), and `sweep_block_jobs()` emits a baseline cell
beside every excluded cell, so for P pages it is 2P in phase 1 and 4P more once phase 2 adds the
cache-off and cache-priming modes: 6P in total. On a site with 36 profiled pages that is 72 then
216, for a single plugin. Nothing in the UI said so, and "216 measurements for one plugin" reads
as a bug until you can see it is one plugin measured on every page in every cache mode.

`SSPA_Run_Controller::status()` now returns `recent`, the last 40 completed measurements as
`{i, label}`, alongside `current`. Both labels come from one new `job_label()` helper so the feed
and the "Now testing" line can never disagree. The index is what lets the client append only what
is new: polling `current` alone would silently drop every measurement that starts and finishes
between two polls, which on fast pages is most of them.

The panel is now centred with a dimmed backdrop while running and drops back to the bottom-right
corner when minimised. The feed follows the tail unless the reader has scrolled up.

**Two bugs found while verifying it in the browser, both of which the code review had missed:**

- The minimise button never worked. The delegated handler was bound to
  `'#sspa-runner .sspa-runner-toggle, #sspa-runner .sspa-runner-head'`, and the button sits inside
  the head, so one click matched both selectors and jQuery invoked the handler twice - toggling
  the class and immediately untoggling it. Confirmed by counting invocations in the page: two per
  click, with `sspa-runner-min` false afterwards, while clicking the title instead worked. Fixed
  by binding to the head alone, which the button bubbles to.
- The feed never auto-scrolled. The "only follow the tail if the user has not scrolled up" check
  ran *after* appending, and a batch of new lines is indistinguishable from the user having
  scrolled away. The decision is now taken before the append.

### A measured verdict now says when it was measured

> * Measured impact now says when it was measured, and warns when that Deep Analysis ran before
>   the analysis shown beside it or against a version you no longer run.

**The symptom, found on the live site.** superspeedyplugins.com showed Super Speedy Search adding
**18,063ms** on `admin-orders-search`. The 18-second admin order search was real, and was fixed in
Super Speedy Search 5.58.1, which was installed. The number was six days old:

```
plugin: super-speedy-search   page_key: admin-orders-search
normal:   18,062.8ms  measured  test_run_id=5  2026-08-03 19:51:49
disabled: 18,133.3ms  measured  test_run_id=5  2026-08-03 19:51:49
prime:    18,254.7ms  measured  test_run_id=5  2026-08-03 19:51:49
```

Meanwhile the attribution columns on the same row came from run 101, ninety minutes old, showing
154.6ms across 22 queries. Two runs six days apart, side by side, with nothing to say so.

The cause is structural rather than a bug: attribution comes from the latest baseline or spot run,
while Measured impact comes from `MAX(test_run_id)` per plugin - each plugin's own most recent deep
sweep, which is only refreshed when someone runs Deep Analysis again.

**The fix.** Every measured cell now carries its provenance line, from two independent staleness
signals because they catch different things:

- the impact's `plugin_version` differs from the version the attribution run recorded. Exact, but
  only works on rows written since 0.12.1;
- the impact's `test_run_id` is older than the run being displayed. Always available, and the only
  one that catches historical rows like the 18-second one above.

Either fires a `sspa-impact-stale` line telling the user to re-measure; otherwise the cell simply
states the date, and the version when it has one.

### Deep Analysis can be scoped to specific pages

> * Deep Analysis now accepts a page list, so `wp sspa run --type=deep --suspects=my-plugin
>   --pages=admin-orders-search` re-measures one plugin on one page instead of sweeping every page.

`--pages` was documented and accepted for every run type, and **silently ignored for deep runs**:
`build_sweep_jobs()` derived its page list solely from the source run's profiles and never looked
at `$args['page_keys']`. So the one case where scoping matters most - re-measuring a plugin you
have just fixed, to clear a stale verdict off the Plugins tab - still cost a full sweep. On
superspeedyplugins.com that was 216 measurements where 6 would do.

The page list is now intersected with what the source run actually profiled, and a page the source
run never profiled is refused with `sspa_pages_not_profiled` rather than silently falling back to
everything - there would be no baseline to compare against.

### The attribution switch stopped reloading the page

> * The Attribution Code owner and Caller buttons on the Plugins tab now swap the table in place
>   instead of reloading the page.

They were `<a href="?attrib=...">` links, the only control on a screen where everything else
updates in place. Now `wp_ajax_sspa_attribution` returns the re-rendered table, the JS swaps it,
updates `aria-pressed` and the mode description, and `history.replaceState` keeps the mode
deep-linkable without navigating.

The table rendering moved out of `includes/admin/tabs/plugins.php` into
`includes/admin/class-sspa-plugins-table.php` so the initial render and the AJAX response come from
one method. Two copies would have drifted the first time a column changed - and a column had just
been added.

Verified in a real browser with Playwright: a sentinel written onto `window` before the switch
survives it, proving no page load; `aria-pressed`, the active button, the description and the URL
all update, the Plugins tab stays selected, and the console stays clean.

### The whole screen stopped reloading

> * Nothing on the Performance Analysis screen reloads the page any more: queueing a run,
>   pruning detailed data, replacing a drop-in, retrying or pausing a submission, cancelling a
>   run and finishing an analysis all update in place, keeping the tab you were on.

> * The Sharing settings and Choose analyses links now switch tab in place instead of reloading
>   and landing you back on Overview.

Pressing "Queue latest run" reloaded the page. An audit found **nine** `window.location.reload()`
calls and two cross-tab links that navigated - on a screen where tabs are hash-driven and every
other control updates in place. A reload loses the selected tab, the scroll position and any open
drill-down, and on a slow admin it reads as the button having gone wrong.

The two links were worse than a reload: they pointed at `admin.php?page=sspa&tab=share`, but tab
selection is driven by the URL hash, so they reloaded the page *and* landed the user back on
Overview.

`SSPA_Run_Controller::ajax_render_tab()` generalises what the Tools tab already did for itself:
it re-includes one or more tab templates and returns their HTML. Each tab file is already a
self-contained template that fetches what it needs, so that is the entire implementation. Tab
names go through `sanitize_key()`, which leaves only `[a-z0-9_-]`, so no path can escape the tabs
directory, and the response carries the current active run id so the runner's state stays honest.

Each action now re-renders only the tabs it affects: pruning touches Overview, Tools, History and
Share; queueing touches Share and History; a finished run touches all five. `sspa_runner_finish()`
no longer reloads after a 1.5s delay - it refreshes the tabs and takes the panel down, so results
appear under whichever tab the user was already reading.

Verified in a real browser by stamping a sentinel onto `window` before acting: it survives
queueing a run and both cross-tab links, which a page load could not.

### A four-part version number blocked every submission a site could make

> * Fixed sharing being refused on any site running a plugin with a four-part version number,
>   e.g. 3.0.83.3, which the privacy check mistook for an IP address.

**Found by dogfooding, not by the suite.** superspeedyplugins.com had `sspa_share_optin = 1` and
six completed runs, and its outbox was empty - not one payload had ever been queued.
`sspa_submission_build_errors` held six identical failures:

```
sspa_privacy_forbidden_value
Potential private data at $.component_inventory.56.version.
```

Component 56 was `syntax-highlighter`, version **`3.0.83.3`**. `validate()` scans every string for
a dotted quad to catch IP addresses, and a four-part version number is character-for-character an
IPv4 address. So the site rejected its own payloads, every time, into an option nobody reads.

This is the same failure shape as `distinctive_db_name()` earlier in 0.12: a needle broad enough
to match something present in *every* payload stops the site submitting at all, rather than
filtering one value. Four-part versions are common in older plugins, so this would have silently
muted an unknown share of installs.

**The fix** exempts exactly one combination: a value under a `version` or `*_version` key that
matches the `safe_version()` character class. That class admits no scheme, `@` or `/`, so such a
value cannot be a URL, an email or a path - the dotted quad was the only pattern it could trip.
The site-identifier needle scan still runs on version values.

Proved narrow by disabling the exemption: the two version assertions fail while "an IP address in
an ordinary field is still rejected", "a version field cannot smuggle a URL" and "...a filesystem
path" all still pass.

Nothing was lost on the affected site: those runs have no outbox row, so `Queue existing runs`
backfills them.

Related, and still open: the build errors that recorded this are written to
`sspa_submission_build_errors` but the Share tab only surfaces that list for the backfill path, so
a site muted this way has no way to find out. See `.docs/2026-08-09-community-submission-review.md`
finding 3.6.

### Option access tracking, and autoload advice that names actual rows

> * Every analysis now records which options each page actually read, so the Overview can name
>   the autoloaded options no page used and the size they cost on every request.

> * New Autoloaded options panel on the Overview, with copy-and-paste SQL to switch autoload off
>   for options nothing read and on for options read on nearly every page.

Design and the measurements behind it: `.docs/2026-08-09-option-access-tracking.md`.

**The gap.** `autoload_bloat` has existed since the first release: it compares
`demographics.metrics.autoload_bytes` against 1 MB and tells the user to *"find the biggest
autoloaded rows and set autoload=no"*. The plugin could not tell them which rows, which makes it
advice rather than analysis.

**The collector.** WordPress 6.1 added a generic `pre_option` filter that fires for every
`get_option()` call, receives the option name, runs before the alloptions/cache/DB lookup, and
still fires when a per-option filter has already short-circuited. Returning `$pre` untouched makes
it a pure observer.

It is registered in **`dropins/db.php`, not the mu-plugin**, and that is the whole design. Load
order in `wp-settings.php`: `require_wp_db()` at :136, `wp_not_installed()` at :180 which reaches
`wp_load_alloptions()` via `is_blog_installed()`, then mu-plugins at :498. An observer armed from
the mu-plugin misses `siteurl`, `home`, `blog_charset`, `active_plugins` and the entire autoload
prime, and would then report the options every single request needs as never read - producing a
recommendation to de-autoload exactly the wrong rows. `mu/sspa-loader.php` carries a fallback for
sites whose `db.php` is absent or owned by another plugin; it marks the capture
`coverage = 'partial'`, and `autoload_coverage()` refuses to emit any recommendation from partial
data.

Names and call counts only. Option values hold licence keys, API tokens, SMTP passwords and
customer email addresses, so they are never recorded; the test asserts the fixture's value string
appears nowhere in the capture or the generated SQL. Own `sspa_*` rows are excluded at collection,
distinct names are capped at 3,000 with a `truncated` flag, and a truncated capture is also refused
for recommendations.

**Rank by bytes, never by count.** Measured on a clean dev site before any of this was designed:
327 autoloaded options totalling 71 KB, of which **155 were never read across five page types and
were worth 5 KB between them** - and 3 KB of that was a single row. A count-ranked finding would
tell that user to edit 155 rows to save 5 KB. So `autoload_coverage()` gates on
`autoload_unread_bytes` (100 KB) and names only rows at or above
`autoload_option_floor_bytes` (1 KB). On a full 27-profile scan of the dev site it correctly named
exactly one row.

**The reverse recommendation.** The same run found 93 options read on nearly every page that are
*not* autoloaded, each paying for its own lookup. `autoload_missing_page_ratio` (0.8) and
`autoload_missing_max_bytes` (20 KB) select those. This is the safer half: autoload is only a
caching decision, so a wrong call costs speed and never correctness, but turning autoload *on* for
something genuinely read everywhere cannot regress anything.

**Coverage floor.** `autoload_min_pages` (5) exists because "read on 80% of pages" is meaningless
across two, and a single-page adhoc run would otherwise recommend autoloading everything it saw. A
full scan covers roughly 30 page types, so the floor only ever excludes thin runs. Transients are
excluded in both directions - WordPress manages them, and under an external object cache they never
touch the options table at all, so their absence proves nothing.

**It needed its own place on the screen.** First cut put it in Top insights, which shows five
findings ranked by severity then impact. It is a `warn`, and any real site has several critical
per-page query findings above it: on superspeedyplugins.com it correctly identified **374 KB of the
639 KB autoload set as never read across 37 pages** - `sccss_settings` 35 KB, `wpseo_titles` 25 KB,
`rank_math_video_posts` 23 KB, plus leftovers from plugins and themes no longer installed - and was
still invisible, ranked below a slow query on one page. A site-wide configuration finding with
copy-and-paste SQL is not the same kind of thing as a per-page query finding and should not compete
with one. `SSPA_Insights::STANDALONE` now excludes it from `top()`, `standalone()` fetches it, and
the Overview renders it in its own panel where the SQL has room.

**Output.** `SSPA_Insights::render()` gained an `sql` field, rendered untruncated in a scrollable
block on the Overview (the existing `detail` is cut at 400 characters, and a statement cut off part
way through is worse than useless). The statement matches the site: WordPress 6.6 replaced
`'yes'`/`'no'` with `'on'`/`'off'`, so `wp_autoload_values_to_autoload()` decides which to emit, and
the block ends with the `wp cache delete alloptions options` the change needs to take effect.

Evidence carries the option names locally but the submission gate allow-lists numeric keys only, so
`unread_bytes`, `unread_count`, `missing_count` and `pages_covered` were added to
`SSPA_Community_Privacy::finding_evidence()` and the names are dropped from anything shared.

`.tests/cases/26-option-coverage.php` plants a 40 KB autoloaded option nobody reads and a small
option a fixture plugin reads on every request, drives a real six-page run, and asserts full
coverage, that `siteurl` was observed (the bootstrap option a late-armed observer would miss), that
each fixture lands on the correct side of the recommendation, that no value appears anywhere, and
that a single-page run produces no recommendation at all.

### Claiming a queued submission became atomic, and a dead attempt stopped burning the backoff

> * Queued submissions are claimed atomically, so two background workers can never deliver the
>   same payload twice.

> * A submission interrupted by a PHP timeout now waits for its scheduled retry instead of
>   becoming due again immediately.

**What it was.** `SSPA_Community_Outbox::due()` is a plain `SELECT ... LIMIT 1` and
`begin_attempt()` was an unconditional `UPDATE ... WHERE id = %d`. Nothing decided ownership at
the database. The only exclusion was `SSPA_Community_Worker::lock()`, a read-then-write lease
over `add_option()` - and `add_option()` short-circuits on a cached `get_option()` while its
write is `INSERT ... ON DUPLICATE KEY UPDATE`, so two simultaneous requests can both be told
they hold it. Two overlapping WP-Cron spawns could therefore select and submit the same row.
Only the receiver's `submission_uuid` idempotency stopped that becoming duplicate archived
submissions, which is why it never surfaced.

Separately, `begin_attempt()` set `state='retry'` and incremented `attempts` but left
`next_attempt` untouched. One attempt can spend 30s reserving, 120s uploading and 120s
completing; if PHP times out in the middle, neither `sent()` nor `failed()` runs, the `finally`
that releases the worker lease does not run either, and the row is left in `retry` with a
`next_attempt` already in the past. Once the 300-second lease expired the row was immediately
due again, incremented `attempts` again, and walked 15min/1h/6h/24h in a few minutes of wall
clock without ever having waited out a single interval.

**What it is.** `begin_attempt()` is now a compare-and-set on `(id, attempts, state)`:

```sql
UPDATE ... SET state='retry', phase='reserving', attempts = %d, next_attempt = %s
 WHERE id = %d AND attempts = %d AND state IN ('pending','retry')
```

Including the `attempts` value the caller read makes it a true CAS - two workers that both saw
`state='retry'` still cannot both win, because only one can move `attempts` from N to N+1. The
method returns `null` when it loses, and `SSPA_Community_Worker::run()` returns without
submitting rather than proceeding with a row it does not own.

The same statement sets `next_attempt` to now + `ATTEMPT_LEASE_SECONDS` (600), comfortably past
the 270 seconds of HTTP timeouts one attempt can consume, so an in-flight row is not due again
while it is running and a crashed one is indistinguishable from a scheduled retry.
`sent()` and `failed()` both overwrite `next_attempt` on the normal paths, and `retry_now()` and
`resume()` set it to now, so a manual retry still bypasses the lease immediately.

`.tests/cases/20-community-outbox.php` proves both: the first `begin_attempt()` returns the row
with `attempts = 1`, a second call with the same stale snapshot returns `null` and does not
consume an attempt, and the claimed row's `next_attempt` is more than a minute in the future.

### Admin assets stopped being served stale

> * Admin styles and scripts refresh as soon as they change, so the analysis screens cannot
>   render with a stale stylesheet.

**The symptom.** After the tab-bar and Plugins-tab work in this release, the analysis screen
rendered with the new HTML and the previous stylesheet: the title did not sit in the tab row and
the page looked broken. A hard reload fixed it, which is the tell.

**The cause.** `wp_enqueue_style()` and `wp_enqueue_script()` were passing `SSPA_VERSION` as the
cache key for every bundled asset. That is correct across releases and useless within one:
editing `sspa-admin.css` or `sspa-admin.js` without bumping the plugin version leaves the URL
identical, so every browser that had already loaded the screen kept its cached copy. The failure
mode is indistinguishable from broken CSS or dead JavaScript, which makes it expensive to
diagnose.

**The fix.** `sspa_asset_version()` in `defines.php` returns `SSPA_VERSION . '.' . filemtime()`
for a bundled asset, falling back to `SSPA_VERSION` alone when the file is missing. All five
enqueues use it - the two admin assets plus `sspa-adhoc.css`, `sspa-adhoc.js` and
`sspa-checkout.js`. `.tests/cases/25-admin-assets.php` touches the stylesheet and asserts the key
moves with it.

Verified in a real browser with Playwright against the dev site, driving the page with a wp-cli
minted session cookie: the brand and the tabs share a row, the wrapper computes to `display: flex`,
the version pill renders, all three tab switches work and the console is clean.

### The community submission path became a durable outbox

> * Sharing your results with the community is now a durable background queue: each completed
>   run becomes its own versioned anonymised payload, which survives reloads and outages and
>   retries until the community archive confirms it is stored.

> * Analysis runs never wait on the network, so the community archive being unreachable cannot
>   slow down or fail a run.

**What it was.** Schema 1 built a payload inside `SSPA_Anonymiser::build()` every time Submit
Now was pressed, and `SSPA_Submitter::submit()` POSTed it synchronously. Nothing was stored, so
two presses could send two different payloads for the same run; a hub outage lost the data
outright; and the hub calls used `'sslverify' => false`.

**What it is.** `SSPA_Community_Outbox::queue_run()` encodes the payload once, gzips it once at
level 6, hashes those exact bytes once and stores them in `sspa_submission_outbox` with a
`submission_uuid` that is generated before encoding, so the UUID is part of the immutable
payload. The bytes are never rebuilt. `SSPA_Community_Worker` is a bounded WP-Cron runner that
takes one due row per invocation behind an option lease, and only `SSPA_Community_Outbox::sent()`
- reached solely through a receipt whose submission UUID, `storage_status=archived` and SHA-256
all match under `hash_equals()` - can move a row out of the retry cycle.

Retries back off 15 minutes, 1 hour, 6 hours, 24 hours, then daily, with jitter, and never give
up. `Retry-After` is honoured for 429 and 503. Connection failures, timeouts, 408, 425, 429,
500, 502, 503 and 504 are retryable; everything else is a visible permanent failure rather than
a silent one. The state machine always restarts at reservation after a PHP timeout or process
death, because the receiver, not the client, is the authority on whether the upload or the
completion still needs doing.

Runs are given a persistent `run_uuid` and a `measurement_version` (migration assigns a UUID to
every pre-existing run), and the outbox has a unique index on `run_uuid`, so a run cannot be
queued twice.

### One coherent run per submission, covering every profiling mode

> * Deep analyses, cache analyses, checkout flows, ad-hoc page profiles, plugin-toggle spot
>   checks and Excimer function, component and phase data are all shared now, each as one
>   coherent run rather than a mixture of the latest profiles and unrelated history.

**What it was.** Schema 1 took the latest completed `baseline` or `spot` run, and then appended
the newest global deep impacts and a small cache-impact summary regardless of which run had
produced them. It exported no Excimer data at all - no functions, no components, no phases -
and skipped `adhoc` and `checkout` runs entirely. Plugin versions came from the site's *current*
active plugins rather than the inventory captured when the measurement was taken, so historical
evidence was attributed to whatever happened to be installed at submission time.

**What it is.** A submission is one run. `SSPA_Community_Exporter` projects that run into an
envelope carrying `payload_schema` major/minor, an `evidence_manifest` and an `evidence` array
of namespaced, individually versioned records: `sspa/site-snapshot`, `sspa/page-profile`,
`sspa/component-observation`, `sspa/excimer-profile`, `sspa/finding`, `sspa/plugin-impact`,
`sspa/cache-impact`, `sspa/checkout-flow`, `sspa/plugin-toggle-spot` and
`sspa/adhoc-page-profile`. The manifest is deliberately redundant so the receiver can later
prove processing did not skip records.

Six version numbers are kept independent - client, transport, payload schema major/minor,
anonymisation, measurement, and per-evidence-type - as integers, never a float. That is what
lets a processor tell evidence v1 from v2 without inferring it from the plugin version, and
lets a future processor reprocess only the subset it newly understands. `sspa/page-profile` and
`sspa/checkout-flow` are already at evidence version 2 while everything else is at 1.

The activation/deactivation prompt used to delete its transient before starting the spot run,
losing the only record of which plugin had been toggled. The slug, action and version are now
persisted into the run's local `share_context` at run creation and exported as
`after_toggle_observation` - explicitly an after-only observation, not a causal impact, because
no paired before/after measurement exists. A real paired method later gets its own measurement
version and evidence class rather than quietly reusing this one.

### Ad-hoc page profiles carry no URL and no URL-derived key

> * Ad-hoc page profiles are shared as a page classification and an opaque identifier, so no
>   URL or URL-derived key leaves your site.

The local report still uses the URL; the submission never does. Nor does it use a hash of the
URL: common WordPress URLs are a small enough set to dictionary-guess from a deterministic
hash, so a hash would have been an identifier wearing a disguise. Unknown URLs collapse to a
coarse `custom-frontend` or `custom-admin` classification, and the evidence is tied together by
an opaque per-submission evidence UUID instead. Schema 1's deterministic domain hash is gone
for the same reason, and the new protocol does not need it.

`SSPA_Community_Privacy` is a hard gate rather than a filter: it runs before the payload can
enter the outbox, and a violation aborts queueing with a local error naming the evidence path.
Domains, URLs, paths, query strings, raw SQL and SQL literals, emails, IPs, usernames, customer,
user, session, cart and order identifiers, cookies, nonces, tokens, headers, request and
response bodies, filesystem paths, checkout form values and free text are all forbidden
outbound. It is defence in depth on top of the exporters, not the anonymiser - nothing is left
for the receiver to clean up.

### Direct upload on a short-lived single-object URL

> * Payloads upload straight to the community archive using a short-lived single-object URL
>   issued by superspeedy.org, and TLS verification is always on.

Three HTTP requests present as one idempotent operation. `POST /v1/submissions` reserves against
a transport manifest signed with HMAC-SHA256 over a fixed newline-delimited canonical string
(`SSPA-SUBMISSION-RESERVE-V1`), sent as `X-SSPA-Signature` with the installation UUID in
`X-SSPA-Install`. The receiver replies with a five-minute presigned URL scoped to that exact
object key, the bytes go straight there with `wp_remote_request()` PUT and
`Content-Type: application/gzip`, and `POST /v1/submissions/<uuid>/complete` closes it with a
second canonical string (`SSPA-SUBMISSION-COMPLETE-V1`).

No AWS SDK and no object-store credential is in the plugin. The install generates its own random
32-byte secret, sends it once to `POST /v1/installations` over verified TLS, and uses it locally
for HMACs; the receiver hands back no long-lived credential. The secret is stored in a
URL-scoped, non-autoloaded option, so a development collector and the production one cannot mix
credentials. Presigned URLs and secrets are excluded from the events table, the UI and support
diagnostics. Every `'sslverify' => false` from the schema-1 hub calls is gone.

An expired presigned URL is not an error worth surfacing - the next reservation returns a fresh
one. A lost completion response is not a re-upload - the client restarts at reservation and the
receiver reports whether the object already arrived.

### Historical backfill

> * New `Queue existing runs` control shares the analysis history you already have, in bounded
>   resumable batches, skipping runs that are already queued or archived.

`SSPA_Community_Backfill` inventories eligible runs first and shows the counts by type, how many
still hold detailed captures versus scalar summaries only, the estimated compressed size and how
many are already queued or archived, before creating anything. It works in bounded batches and
resumes where it stopped.

Where `profile_blob` has already been pruned it exports the remaining safe scalar evidence with
explicit missing-evidence markers. It does not invent zeroes, does not guess a plugin version
that was never recorded, and never borrows evidence from another run to make a historical
submission look complete. Failed checkout runs with valid partial step evidence are included as
`outcome=failed` and explicitly incomplete; cancelled and corrupted runs are not submitted.

For opted-in sites, local pruning now waits until the corresponding outbox item exists. Once the
exact bytes are stored, later pruning cannot change them.

### Consent, preview and queue controls

> * The Share tab previews the exact JSON each queued payload would send, with its compressed
>   size, SHA-256 and receipt.

> * New `Retry now`, `Pause` and `Resume` controls per queued payload, replacing the old Submit
>   Now button, which rebuilt a payload from scratch on every press.

> * Sharing stays off until you opt in, an update never turns it on, and turning it off stops
>   new payloads and delivery attempts without deleting anything already archived.

Preview decompresses the stored bytes and verifies both the length and the SHA-256 before
displaying them, so what the Share tab shows is provably the payload that would be sent, not a
regenerated approximation. Consent carries a version number. Pause is non-destructive: it stops
delivery attempts and leaves the bytes alone. The agent/ability surface can queue an already
opted-in site's data but cannot turn sharing on.

### Sharing one analysis without sharing everything

> * New `Share this` control on every analysis in the History tab, so you can contribute a
>   single full scan, deep analysis, page analysis, cache analysis, spot check or checkout
>   analysis without switching on sharing for everything else.

> * The Share tab now presents the two choices separately: share every analysis automatically,
>   or pick individual analyses and share only those.

Consent now has two scopes rather than one. `sspa_share_optin` means "share every analysis I
run, now and in future"; a `Share this` click is its own act of consent for exactly one run.
Outbox rows carry `consent_scope` (`automatic` or `manual`, schema 1.5) to record which applied.

`SSPA_Community_Outbox::due()` became the single authority on what may leave the site: with the
site-wide setting off it returns nothing but `manual` rows. The worker no longer makes that
judgement itself, so there is one place to reason about, and an opted-out site with fifty
automatically queued analyses from a previous opt-in period delivers only the ones the owner
has since picked. A per-run share never enables the site-wide setting, and the agent/ability
surface still cannot enable it.

A manually shared payload records `client.consent_version` as the version in force at the
moment of the click, rather than the site-wide option, which is `0` on a site that never
accepted the blanket setting. Reporting `0` on a run the owner had explicitly chosen to share
would have been wrong in the permanent archive.

The History tab gained a "Share with community" column showing either the queue state - with
`(this run only)` for a manual share - or a button naming what it would send, so the wording is
"Share this checkout analysis" rather than a generic Submit. The control reports its result in
the cell next to the run rather than through `confirm()`/`alert()`.

### The privacy gate blocked every submission on a site called `wordpress`

Not a customer-facing entry: the collection feature had not been released, so nobody could have
hit this. It is recorded because of how it was found and how nearly it went out.

`SSPA_Community_Privacy::validate()` treats `DB_NAME` as a site identifier and scans every
string in the payload for it as a raw substring. The WordPress.org and Docker default database
name is literally `wordpress`, which is a substring of the plugin's own `wordpress-core`
sentinel slug - present in the component inventory of every payload ever built - and of real
public slugs such as Yoast's `wordpress-seo`. On any site whose database is called `wordpress`,
every analysis of every type failed to queue with `sspa_privacy_site_identifier`, permanently.
The same function already carried this exact fix for bare hostnames ("Bare Docker/intranet
hostnames commonly collide with plugin slugs"); database names needed it too.

`distinctive_db_name()` now drops generic database names, and a real database name that appears
in SQL was already replaced outright by `sql_fingerprint()`, which is where one would actually
show up.

It survived every existing test because the manual live fixtures build their own component
inventory containing a single `woocommerce` entry, and the production smoke test therefore
never included `wordpress-core`. It was found the moment a test drove real analyses through the
real run controller with sharing on - which is what case 23 now does.

### Excimer installs via the distro package, targeted at the site's PHP version

> * The excimer install steps now use your distribution's package (`php8.3-excimer` style
>   on Debian and Ubuntu, Remi's `php-pecl-excimer` on RHEL and Fedora,
>   `php83-pecl-excimer` on Alpine), named for the exact PHP version the site runs so
>   servers carrying more than one PHP enable it for the right one; pecl remains only
>   where no package exists, as upstream no longer publishes excimer releases there.

**The trigger.** Upstream's page (mediawiki.org/wiki/Excimer) now states PECL is
deprecated and new releases will not be published there - and PECL itself carries a
platform-wide deprecation banner pointing at PIE. Excimer 1.2.6 (April 2026) is the last
version on PECL. Verified availability at the time of writing: Debian trixie 1.2.3, Ubuntu
noble 1.1.1 / jammy 1.0.2 (stock), deb.sury.org 1.2.6 built for every PHP 7.1-8.5, Remi
`php-pecl-excimer`, Alpine `php8X-pecl-excimer` 1.2.6. Our profiler only uses the base
`ExcimerProfiler` API, present since 1.0, so any of those versions works.

**Why the package beats pecl anyway.** A pecl-compiled `.so` is built against one PHP API
version; the next PHP upgrade moves the extension dir and the profiler silently vanishes
from the site. The distro package rebuilds with PHP through the package manager, ships its
own ini and enables itself - so the packaged path is three steps (install, restart,
verify) with no build tools and no hand-written ini, where a leftover manual
`20-excimer.ini` would collide with the package's identically-named symlink.

**The versioned-name trap, hit live.** Migrating the production superspeedyplugins box
(noble + sury, site on PHP 8.3 FPM, 8.5 also installed) showed that sury's unversioned
`php-excimer` is a metapackage that installs for the repo's *newest* PHP - it enabled
excimer for 8.5 and left the site's 8.3 without it. The generated command therefore leads
with `php<major.minor>-excimer` derived from the PHP actually serving the site, with an
unversioned fallback commented for stock Debian/Ubuntu, which only carry `php-excimer`.
The verify step names the versioned CLI binary (`php8.3 -m`, `php83 -m` on Alpine) for the
same reason, and points at the Tools tab Re-check as the authoritative test since it asks
the exact PHP process serving the site.

### tideways_xhprof was never on PECL

> * The `tideways_xhprof` install steps now build the extension from its source
>   repository, `github.com/tideways/php-xhprof-extension`.

Found while in the file: the generated step said `sudo pecl install tideways_xhprof`, but
no such PECL package has ever existed (pecl.php.net/package/tideways_xhprof is a 404 -
PECL's `xhprof` is the original extension, a different API). The command would have failed
on every system. It is now a source build with the same shape as SPX, and the build-tools
step for source builds asks for git plus a compiler instead of php-pear. `host_message()`
was updated in the same pass: the ask-your-host ticket now gives the distro-package
commands for excimer (naming the site's PHP version so a multi-PHP host installs for the
right one) and the source-build commands for tideways_xhprof and SPX.

`15-tools.php` pins all of it: packaged distros get exactly 3 steps with no `pecl
install` and no hand-written ini, apt commands must carry the running PHP's version, the
verify step must not use plain `php -m` on apt/Alpine, and tideways_xhprof must reference
its real source repo. Suite run in the Docker env (WP 7.0.2, Alpine 3.24, so the apk path
was exercised live): 0 failures.

## 0.11.3 (7th August 2026)

### Deterministic misbehaviour signatures

> * New deterministic misbehaviour signatures in the checkout analysis ...

The three patterns the live run exposed are general - any HPOS store running nginx-helper
(every GridPane site ships it preconfigured) exhibits the first, and the others are common -
so they are now recognised mechanically. `SSPA_Analysis_Engine::checkout_http_signatures()`
evaluates closed predicates over the captured outbound calls:

- **order_page_purge**: a blocking call to this site whose `?p=` value is one of the run's
  own order ids (now recorded in the run notes precisely for this). Deterministic because
  the placeholder post id IS the order id, on both HPOS and legacy storage. Always critical:
  purging an order's "page" is wrong on every store.
- **amp_purge_missing**: a blocking self-call whose path ends `/amp/` while no AMP plugin is
  active (`AMP__VERSION` / `AMPFORWP_VERSION` / `amp_is_enabled`).
- **self_fetch_failed**: a blocking self-call that errored at or beyond
  `checkout_self_fetch_ms` (feed threshold, default 1000ms).

Design decision, deliberately recorded: **predicates are code, copy and thresholds are
data**. The recommendations and thresholds ride the existing signed superspeedy.org rules
feed (bundled snapshot as offline fallback), so wording improves and thresholds tune without
a release; the matching logic stays in PHP because three signatures do not justify a
predicate DSL. If the catalogue grows past a dozen, the intended evolution is a
closed-vocabulary condition schema in the feed (`fact`/`op`/`value` triples over the same
call fields) evaluated by a small interpreter - still fully deterministic, never an LLM.
Matching is by behaviour, never plugin name, so hosting-company forks attribute correctly
via the component map.

To make the `?p=` check possible the capture now keeps VALUES for a whitelist of routing
keys (`p`, `page_id`, `post_type`, `attachment_id`, `paged`) that cannot carry secrets;
every other query key remains key-only.

Case 19's fixture now mimics all three behaviours (an `?p=<order id>` fetch, an `/amp/`
fetch, and a 1.4s endpoint hit with a 1s timeout) and asserts each signature fires and is
attributed to the fixture plugin: 99 assertions.

The companion fix lives outside this plugin: `scalability-pro/.docs/2026-08-07-checkout-
purge-shield.md` designs the spro filters that neutralise all three behaviours reversibly
(unhook nginx-helper's order-note comment purges, short-circuit self-fetches of
non-viewable permalinks and phantom `/amp/` URLs at `pre_http_request`, make `/purge/`
traffic non-blocking).

## 0.11.2 (7th August 2026)

Driven by the first checkout-flow run against the real superspeedyplugins.com store, which
surfaced one measurement-contamination bug, one boundary-placement bug, one cleanup gap, one
counting bug and two display gaps. The diagnosis is worth recording because the raw numbers
looked wrong and were in fact three-quarters right.

### The run that prompted it

The live run reported a 28.3s customer wait with nginx-helper attributed 25.77s. Reconciling
the outbound-call list against the roll-up showed the attribution was arithmetically sound -
nginx-helper really did spend that wall time blocked in its own HTTP calls - but ~6.2s of it
belonged to the harness's delete step and pre-flight, not the purchase. Pulling the stored
capture off the live site (the per-call `caller` field, which the panel did not yet display)
plus the live `rt_wp_nginx_helper_options` row and the nginx-helper source gave the full
chain:

- Every order status change and order note makes nginx-helper purge the "post" behind the
  order. With HPOS that post is a `shop_order_placehold` draft whose permalink is
  `/?p=<id>` - and the capture dropped query strings from display, so those showed as
  fetches of the bare homepage. Each one hung ~4.5-4.7s and died as
  `error:http_request_failed` (WP's default 5s timeout), three times inside place-order.
- `purge_amp_urls` fetches `<url>/amp/` RAW - no `/purge/` prefix - so on a store with no
  AMP pages each "purge" renders a full 404 page (~750ms each).
- The author-archive purges (`/author/sspa-test/`) exist because guest checkout is disabled
  on that store, so the Store API auto-created a customer account for the purchase - which
  the 0.11.1 cleanup did not remove. Real residue in a real user table.
- Mailgun's HTTP mode replaces the pluggable `wp_mail()` and never fires
  `wp_mail_succeeded`/`wp_mail_failed`, so three ~540ms sends were recorded as
  "1 message in 0ms".

### Harness contamination

> * Fixed the checkout flow's own pre-flight and cleanup steps leaking into the component
>   roll-up, the outbound-call list and the mail totals, which could overstate a
>   cache-purge plugin's cost by a quarter.

`waterfall()` collected the Excimer roll-up, the HTTP calls and the mail counts BEFORE the
harness-step exclusion `continue`. The waterfall totals and the findings engine were already
clean; the three panels underneath were not. Collection now happens only for customer-facing
steps, and case 19 plants a fixture that makes an HTTP call during order CANCELLATION -
i.e. during the delete step - and asserts it appears nowhere.

### The payment boundary was on the wrong side of the cascade

> * The payment boundary is now stamped at entry to `payment_complete()` ...

`WC_Order::payment_complete()` runs `woocommerce_pre_payment_complete`, then the status
transition and `save()` - which is where the order emails and everything hooked on the
transition fire - and only THEN the trailing `woocommerce_payment_complete` action we were
marking on. So the emails and purge cascade landed in the at-risk half. In sandbox mode the
gateway has returned successfully before `payment_complete()` is entered, so entry IS the
money-secured moment. The mark moved to `woocommerce_pre_payment_complete` with the trailing
action kept as an isset-guarded fallback. On the live numbers this flips the headline from
"22.8s at risk / 0.1s secured" to roughly "4s at risk / 19s confirmation-wait", which is the
honest story: the card would already be charged; the customer stares at a spinner while
purges time out.

### Auto-created customer accounts are now cleaned up

> * On stores that disallow guest checkout, the customer account WooCommerce creates for
>   the purchase is now deleted with the order ...

`woocommerce_created_customer` fires inside the flow's own place-order request; the account
is marked `_sspa_temp` and recorded in `sspa_flow_temp` immediately, deleted in the same
`finally` as the order, reported in the safety notes (`users_deleted`/`users_left`), and
swept by the hourly janitor (both from the option and by meta scan) if a crashed run
orphaned one. The pre-flight now discloses "this store creates an account for the purchase".
The type-aware `forget_temp_entries()` replaces the old id-only filter so a user entry can
never be dropped by an order-id collision.

### Finding spam, and the two display gaps

One `checkout_blocking_http` finding per component per step (count, total ms, failed count,
hosts, worst call with its caller) instead of one per call - the live run produced thirteen
near-identical criticals. The capture now keeps query-string KEYS (never values - they carry
secrets) so `/?p=123` is distinguishable from `/`, plus a short in-component `trace` of the
calling functions, and the panel prints method, keys and caller on every outbound call. The
`checkout_component_cost` recommendation also stops telling people to run checkout deep
analysis, which is not built yet (T13).

### Pluggable-wp_mail mailers are counted honestly

`mail_deliver_start` now flushes a still-pending send before starting the next one (sends
cannot interleave in PHP), so a mailer that replaces `wp_mail()` has every send counted with
an unknown duration rather than collapsing to one. The waterfall reports an `untimed` count
and the panel says "sent through a mail plugin's own transport - its time appears under
outbound calls" instead of the false "1 message in 0ms". Case 19 proves it with a fixture
that mimics Mailgun's override, guard and all.

Tests: case 19 grew from 54 to 96 assertions, including a forced-account purchase against a
guest-checkout-disabled store asserting zero user residue.

## 0.11.1 (7th August 2026)

### The classic shortcode checkout (T12)

> * The checkout flow now measures the classic shortcode checkout as well as the block
>   checkout, so a store using `[woocommerce_checkout]` no longer gets "Only the block
>   checkout is supported so far".

**Why it moved up the queue.** superspeedyplugins.com's own checkout page is
`[woocommerce_checkout]`, so 0.11.0 could not measure the store it was written on. Checked
before writing anything: the page content is the bare shortcode, and
`CartCheckoutUtils::is_checkout_block_default()` correctly returns false for it - the message
was accurate, not a detection bug.

**The steps** (doc C3): view product, `?wc-ajax=add_to_cart`, cart page,
`?wc-ajax=update_order_review`, checkout page, `?wc-ajax=checkout`, order received, delete.
Nine profile rows rather than the block path's twelve: there is no separate cart API call, no
separate rate-selection call and no draft order.

**The nonces, which are worse than the doc's A7 fact 8 says.** That fact records that
`wp_create_nonce()` binds to the current request's user and session token, so a nonce minted
inside the admin's AJAX request is bound to the admin. True, but incomplete: WooCommerce also
registers `nonce_user_logged_out` and rewrites the logged-out uid to the CART SESSION's
customer id for any action whose name starts with `woocommerce`
(`WC_Session_Handler::maybe_update_nonce_user_logged_out`). So:

- `woocommerce-process_checkout` is bound to a cart-session id that does not exist until
  add-to-cart has run,
- `update-order-review` does NOT start with `woocommerce`, so it stays on the plain
  logged-out uid.

`SSPA_Checkout_Flow::guest_nonce()` handles both: it strips the auth cookies, sets the current
user to 0, and filters `nonce_user_logged_out` at priority 100 - after WooCommerce's own at 10,
which would otherwise bind the nonce to THIS process's cart session. The session id itself is
read back out of the `wp_woocommerce_session_*` cookie that add-to-cart returned, so it is the
loopback visitor's own session rather than a guess.

Get this wrong and every classic checkout POST comes back "We were unable to process your
order, please try again", which reads like a broken store rather than a broken profiler. That
is exactly what the deliberate break produces, and case 19 asserts it does not happen.

**Shipping.** `wc_get_chosen_shipping_method_for_package()` defaults a rate into the session
while the order review renders, so validation passes even if nothing is posted. The flow still
parses the selected rate out of the returned fragment and posts it, because that is what the
browser does; an unparsed fragment is not fatal, it just leaves the default standing, exactly
as an untouched radio group would.

**Payment.** The same two `needs_payment` filters carry over unchanged.
`WC_Checkout::validate_checkout()` skips the gateway check at line 985 and
`process_checkout()` takes the `process_order_without_payment()` branch at line 1380, which
calls `payment_complete()` - so the post-payment cascade and the payment-boundary mark work
identically on both paths. Measured: 199.5ms of a 224.5ms place-order step was pre-capture.

### Cleanup notes were lost on every failure path

> * Fixed the run notes reporting "0 orders deleted" on a checkout flow that failed part way
>   through, when the order had in fact been deleted.

Found while building the classic path, and it affected the block path in 0.11.0 too. PHP
evaluates a `return` expression BEFORE running the enclosing `finally`, so every
`return $result;` inside `run()`'s try block handed back a copy of `$result` taken before
cleanup had recorded anything. The order really was deleted - the finally always ran - but the
run notes and the panel's safety report both said "0 orders deleted, 0 left" on any run that
did not reach the end. Case 19's residue assertions passed throughout because they count
actual orders rather than reading the notes.

Both paths are now separate methods (`run_block()` and `run_classic()`) called from a single
try/catch/finally in `run()`, so no early return can ever be inside the try again.

### Tests

Case 19 gains a classic section: the store is pointed at throwaway shortcode pages and put
back afterwards (the block pages are never edited), and the nine steps, the order status and
total, the payment boundary, real mail delivery and zero residue are all asserted again for
that path. The throwaway fixture products from the failure-path section are now deleted before
it runs - they are cheaper than the real target product, so leaving them published had the
classic run buy one of THEM, which made the stock assertion check a product the run never
touched.

Two assertions pin the nonce binding directly: the place-order nonce must differ both from an

still passes.

## 0.11.0 (7th August 2026)

Phase 1 of the checkout flow profiler, built from `.docs/2026-08-07-checkout-flow-profiling.md`
(tasks T1 to T11 plus the T14 test case). T12 (shortcode checkout), T13 (per-plugin checkout
isolation) and T15 (sandbox gateway adapters) are deliberately not in this release. Built and
tested against WordPress 7.0.2 and WooCommerce 11.0.0; the design doc was written against
WooCommerce 10.9.1 and every load-bearing fact in its A7 list was re-verified against 11.0.0
before any code depended on it.

### Measuring the purchase instead of the checkout page

> * New: "Analyse checkout flow" measures the server time your customer waits through at
>   every step of one real purchase, with every plugin on your site active, split at the
>   payment boundary so time that risks the sale is shown separately from time after the
>   money is in.

**The problem.** `SSPA_Catalogue::build()` profiles `wc-cart` and `wc-checkout` as static
GETs, which renders an EMPTY cart to a visitor with no session. On a block checkout the real
cost lives in POSTs a crawler never sends: `cart/add-item`, `cart/update-customer`,
`cart/select-shipping-rate` and `checkout`. Those two page figures were honest measurements of
something no customer experiences.

**What it does now.** `SSPA_Checkout_Flow::run()` drives twelve steps over loopback as one
routine - the cart item key, the shipping rate id, the order id and the confirmation URL are
each only knowable at run time, which is why this cannot be N independent queue jobs:
pre-flight, view product, add to cart, view cart, load cart data, enter address, select
shipping, view checkout, create draft order, place order, order received, delete order.

Every step is an ordinary profiled request, so the whole existing apparatus - SQL attribution,
HTTP capture, boot timing, the Excimer sampler - applies per step for free. The new transport
is `SSPA_Crawler::send_profiled()`, a sibling of `profiled_request()` that takes any method,
sends a JSON body, carries headers and cookies, and deliberately does NOT follow redirects: a
followed 3xx becomes a GET and would silently measure the wrong thing. `SSPA_Profile_Store`
stopped hard-coding `'method' => 'GET'`, so a POST step is no longer recorded as a page view.

**The payment boundary.** Slowness before the money is captured risks the sale; slowness after
it is a bad impression but the money is in. A single total hides that difference.
`SSPA_Checkout_Flow::mark_payment_complete()` stamps
`$GLOBALS['sspa_marks']['payment_complete']` from a `woocommerce_payment_complete` hook at
`PHP_INT_MIN`, the capture emits a generic `marks` section next to `boot` and `profile`, and
the panel splits the place-order row there. On a measured docker run that was 231ms at-risk
and 198ms post-capture inside one 429ms request. When the mark is absent the panel shows one
combined row and says the boundary could not be determined; it never guesses.

### Skipping the gateway without touching the totals

An earlier draft of the design used a 100% discount coupon to take the order total to zero,
because `WC_Order::needs_payment()` is `has_status(...) && get_total() > 0`. That mechanism is
real, and was rejected for three reasons recorded in the doc, the largest being that a
zero-value order makes integrations do LESS work: fraud screening, accounting sync, affiliate
commission and tax-commit integrations commonly short-circuit on zero-value orders, which
under-measures the exact thing the feature exists to measure.

Instead, two filters applied only on the flow's own profiled request:

```php
add_filter( 'woocommerce_order_needs_payment', '__return_false', PHP_INT_MAX );
add_filter( 'woocommerce_cart_needs_payment',  '__return_false', PHP_INT_MAX );
```

Nothing is created, the cart totals are untouched so shipping and tax calculate in full, and
the order total stays real - £16.00 on the docker store - so downstream integrations see a
normal order. The checkout takes `process_without_payment()`, which calls `payment_complete()`
and runs the entire post-payment cascade: status transition, stock reduction, order emails and
every integration hooked onto them. That cascade is 328 queries on a stock WooCommerce store
with no third-party plugins at all, which is the number this feature exists to attribute.

The gate is written as a **whitelist** of payment modes allowed to take a payment
(`SSPA_Checkout_Flow::PAYMENT_MODES`, currently empty), never as "not sandbox". A missing,
unknown or future flag value falls through to no payment, because getting the default wrong in
the other direction charges someone real money. Case 19 asserts this through the real
armed-request path for three flag shapes - absent, junk, and `pm=s` with no adapter registered
- using a new `npc` probe that reports `needs_payment()` on an in-memory £47 order, so nothing
is created to answer the question.

### A real cart, not an empty one

The first working build had `flow-view-cart` and `flow-view-checkout` rendering an empty cart,
with the checkout page answering 302 and bouncing back to the cart, because the Store API keys
its session to the `Cart-Token` header and never sets a front-end session cookie. That would
have reproduced the exact flaw the feature exists to fix, while looking like a clean run.

WooCommerce 11's `WC_Session_Handler::init_session_from_request()` restores a guest session
from a cart token supplied as `?session=`, for `t_`-prefixed customer ids only. So the first
page view after add-to-cart carries the token and every later one reuses the cookie that came
back - one session for the visit, as a real customer would have, rather than a fresh clone per
page. The session rows the run creates are deleted again by key when it finishes.

The default product also changed: the cheapest purchasable simple product on the WooCommerce
sample dataset is "Single", which is downloadable, so shipping never calculated and
`flow-select-shipping` was skipped. `default_product()` now prefers the cheapest product that
`needs_shipping()`, and only falls back to a virtual one when the store sells nothing physical.
An explicitly requested product that cannot be bought now returns `no_product` rather than
quietly substituting a different one - a silent substitution is a wrong answer that looks like
a right one.

### The disclosure, and what the run leaves behind

The run buys something for real, so the admin sees exactly what it will set off first.
`SSPA_Checkout_Preflight::inventory()` runs on the FRONT END inside a profiled probe, because
an inventory taken from a wp-admin screen misses every front-end-only hook registration. It
reports the enabled transactional emails and their recipients, whether emails are deferred or
sent in-request, active webhooks reduced to their delivery HOST (the full URL routinely carries
a secret and this list is shown on screen), and every component that will run code on the six
order-lifecycle hooks, resolved by reflecting each callback back to its defining file through
the existing component map. Case 19 proves that resolution works on a closure defined in a
planted fixture plugin.

Block-versus-classic detection uses `CartCheckoutUtils::is_checkout_block_default()` rather
than `has_block()` against page content, because a block theme template can supply the checkout
block without it appearing in `post_content`.

Cleanup is layered, because an orphan order in a customer's store is the one outcome this
feature must never produce:

1. every order is stamped `_sspa_temp` as it is created, both by an in-request hook and by the
   driver the moment it learns the id,
2. the id goes into the `sspa_flow_temp` option before the next request goes out,
3. deletion runs in a `finally`, never on the happy path, so any failure after an order exists
   still deletes it,
4. the delete probe and the driver both re-check `_sspa_temp` before deleting anything,
5. the hourly janitor sweeps both the option and any `_sspa_temp` order over an hour old, in
   `wp_postmeta` and the HPOS `wc_orders_meta` table.

Stock is verified rather than assumed. The design doc flagged "cancelled-then-deleted restores
stock" as unconfirmed, so `verify_stock()` compares before and after, puts the number back
explicitly if it has to, and records that it was needed. On WooCommerce 11 it has not been
needed; the check stays because the alternative is trusting it.

### Mail is really sent, for this run type only

> * Order emails are sent for real during a checkout flow run so your mail server's own time is
>   measured; every other kind of run still sends nothing.

Construct mode measures the wrong half for checkout: it builds the message (template cost) and
strips the recipients before transport, so a slow SMTP handshake - a classic reason a checkout
takes four seconds, and squarely in scope - is invisible. The capture gains a third mode,
`deliver`, which intercepts nothing, alters nothing and only times.

One deviation from the design doc. It specified hooking `wp_mail`, `wp_mail_succeeded` and
`wp_mail_failed`. An API mailer that short-circuits `pre_wp_mail` fires neither of the latter
two, so the very case the `wp_mail` hook was chosen to cover would have recorded nothing.
Deliver mode therefore also hooks `pre_wp_mail` at `PHP_INT_MAX` and closes the pending entry
when the incoming value is non-null, and `finalize()` records a still-pending send with an
unknown duration rather than dropping it, because a missing call reads as "no mail was sent".

This deliberately opens a hole in an invariant the plugin otherwise keeps absolutely, so
`mail=d` is reachable only from the checkout flow, whose tokens are minted after an
administrator accepted the disclosure, and it is not the default of any other run type.

### Findings

Five checkout-specific types, with thresholds in the rules feed rather than hard-coded
(`checkout_slow_step_ms` 800, `checkout_component_share_pct` 25, `checkout_http_ms` 50):
`checkout_slow_step`, `checkout_component_cost`, `checkout_blocking_http`,
`checkout_mail_inline` and `checkout_dupe_queries`. They run from
`SSPA_Analysis_Engine::analyse_checkout()`, a separate entry point from `analyse()` because a
flow run has no pages, one sample per step and no baseline, so the page heuristics either do
not apply or would compare against nothing. The pre-flight and delete steps are excluded from
every total there, exactly as they are in the panel.

`checkout_blocking_http` is the one that earns its place: a blocking outbound call inside
place-order or the address step is the classic cause of a six-second checkout. Case 19 plants a
fixture that calls back into the site on `woocommerce_payment_complete` at an endpoint which
sleeps 150ms, and asserts the finding names that plugin - a real call with a repeatable
duration, rather than one that trips the threshold by luck.

### The panel

Waterfall in flow order with the slowest step marked, split into an at-risk half and a secured
half, with the delete step measured but sitting below the total and excluded from it (nobody
waits for admin cleanup). Below that: the findings, mail count with whether it was in-request
or deferred, every outbound call with host and duration, per-component PHP time across the
whole purchase from the Excimer roll-up, and the safety report - orders deleted, orders left,
stock before and after.

It renders into the same popover container as the ad-hoc panel, so it inherits that panel's CSS
wholesale and only its own `sspa-ck-*` additions were needed; interactive elements use
`sspa-ck-*` class names so the two scripts' delegated handlers cannot collide.

`SSPA_Checkout_Flow::rollup_profile()` sums each step's Excimer report by component and by
function. Two limitations are printed rather than hidden: each step's report is already
truncated to its top 40 functions, so this is a sum of top-N lists rather than a whole-flow
profile, and inclusive time cannot be added to self time to make a total. The sampler's own
sanity check - sampled ms against summed step generation time - came out at 0.95 on the docker
run, and case 19 asserts it stays between 0.3 and 1.5.

`SSPA_Excimer::phase_windows()` also stopped labelling the final window `render_and_output` on
REST and `wc-ajax` requests, where there is no template and that window holds nearly everything
the endpoint did. It is now `endpoint_work` there, which matters most on exactly the requests
this feature measures.

## 0.10.11 (7th August 2026)

### The plugin never checked for its own updates

> * Restored the plugin's own update check against superspeedyplugins.com, so new versions
>   show up on your Plugins screen again. If you are on 0.9.3 to 0.10.10, install this one
>   by hand once from
>   https://github.com/superspeedyplugins/super-speedy-performance-analysis/releases/latest
>   and updates arrive on their own from then on.

Found while verifying the 0.10.10 release zip in a clean Docker WordPress 7.0.2 playground -
the brief was "confirm the super-speedy-settings submodule is correctly configured", and it
was not.

**The symptom.** No update was ever offered for this plugin, from any version, on any site.
Nothing failed and nothing was logged; the Plugins screen simply never listed an update.

**The cause.** Settings 1.5.0 (2026-08-03, the candidate-registry "latest copy wins" loader)
turned `super-speedy-settings.php` into a thin facade. It no longer defines anything real -
it queues the copy as a candidate and lets the NEWEST registered copy's
`super-speedy-settings-core.php` load at `plugins_loaded` priority -9999. The PUC library is
required by that core, at line 19.

This plugin required the submodule and then, on the very next lines of its main file, did:

```php
if (class_exists('SuperSpeedy\PluginUpdateChecker\v5\PucFactory')) {
    $sspa_update_checker = PucFactory::buildUpdateChecker(...);
}
```

Plugin main files are included long before `plugins_loaded` fires, so from the moment this
plugin picked up the facade-era submodule that `class_exists` was always false and the
update checker was never built at all. The guard was written for "a zip without submodules",
and it silently absorbed a completely different failure. First affected commit: e2a9cbc
(3rd August 2026), plugin version 0.9.3.

The paid plugins are not affected. They call `SuperSpeedySettings::init()`, and the core
builds their update checkers itself (`super-speedy-settings-core.php:171`) once it has
loaded. This plugin deliberately skips `init()` - it is free, has no licence key, and a
second registration of the same slug fatals PUC - so it is the only one building its own,
and the only one that had to care when the load order changed.

**How it was proven, not assumed.** Reading the code gives you the hypothesis; the evidence
came from the real code path. A `pre_http_request` logger in a mu-plugin recorded every
outbound URL during a genuine logged-in `wp-admin/plugins.php` request with the update
transients cleared. Result: `api.wordpress.org` only (which does not carry this plugin) and
`sspa_update_checker: NOT BUILT`. Positive control - the same harness, with a mu-plugin
building the checker at `plugins_loaded` -9998 - fetched
`https://www.superspeedyplugins.com/assets/plugins/super-speedy-performance-analysis.json?installed_version=0.10.10&php=8.3.32...`,
confirming the harness can see a working checker and that the load order was the whole
difference.

**The fix.** The build moves into an `add_action('plugins_loaded', ..., -9998)` callback -
one tick after the core registers at -9999 - and stores the checker in
`$GLOBALS['sspa_update_checker']`. The `class_exists` guard stays, so a zip genuinely
missing the submodule still activates and simply goes without update checks.

**What this means for installed sites.** Any site on 0.9.3 to 0.10.10 has no working update
mechanism, so it cannot be told about 0.10.11 - the fix cannot reach those sites through the
thing it fixes. They need one manual install, after which the checker is live. Sites still on
0.9.2 or earlier bundle a pre-facade submodule, so their update check works and they will be
offered 0.10.11 normally, provided
`/assets/plugins/super-speedy-performance-analysis.json` on superspeedyplugins.com is
updated to 0.10.11.

## 0.10.10 (7th August 2026)

### The plugin-toggle spot-check looped forever

> * Fixed the spot-check offered after you activate or deactivate a plugin re-running
>   itself every time the page reloaded, instead of stopping once its results were in.

**The symptom.** Reported by Dave against live superspeedyplugins.com. Activate a
plugin, take the "want a 30-second performance spot-check" offer in the admin notice,
land on `admin.php?page=sspa&sspa_autospot=1#overview` - and the page reloads and
re-runs the analysis over and over, with no way out but editing the address bar.

**The cause.** Two pieces of behaviour that are each correct alone. `sspa_runner_finish()`
ends EVERY run with `window.location.reload()`, because the results tabs are rendered
server-side and a reload is how they refresh. And the autospot trigger in the
document-ready handler keys off `window.location.search`, which the reload preserves
verbatim. So a finished autospot run reloaded a URL still carrying `sspa_autospot=1`,
the ready handler saw the flag again and started a fresh run, that run finished and
reloaded, and so on indefinitely. Nothing in the loop was rate-limited: each iteration
profiled home, shop and baseline for real.

The `active-run` guard did not help. It only re-arms the monitor for a run that is still
going; by the time `sspa_runner_finish()` fires, the run is complete, so on the reload
`active` is 0 and control falls through to exactly the `else if` that starts another one.

**The fix.** The flag is consumed once, at page load: `sspa_strip_autospot_param()` reads
it into a local, then removes it from the address bar with `history.replaceState` before
any run is started, preserving the rest of the query string and the `#overview` hash. The
post-run reload therefore lands on a clean `admin.php?page=sspa#overview` and stops. The
strip happens before the active-run branch too, so a reload during an in-flight autospot
run cannot leave a live flag behind either. Browsers without `history.replaceState` (none
that run WP 6.2 admin) simply keep the old behaviour rather than erroring.

Second, smaller half: the `sspa_plugin_toggled` transient was only deleted by the Dismiss
link, so for its full 10 minutes the notice kept offering a spot-check you had already
taken - and every one of those offers was another entry into the loop. Arriving with
`sspa_autospot` now deletes the transient as well, in `toggle_prompt_notice()`.

this a WooCommerce bug or a perf-tool bug?". Answer: likely neither - a measurement-path
divergence. SSPA's profiling requests are server-to-self loopbacks; when the host pins
the domain locally (GridPane commonly does), they bypass Cloudflare entirely and arrive
with NO CDN-added headers. WooCommerce then correctly runs MaxMind on the measured path
while real visitors (whose requests carry CF-IPCountry) correctly skip it. The tool was
honestly measuring a path visitors do not take, and saying nothing about it.

Fix: the capture (which runs INSIDE the profiled request) records
`overview.via_cloudflare` (HTTP_CF_RAY present) and `overview.cf_country`
(HTTP_CF_IPCOUNTRY). The panel renders one of:

- "went directly to origin, not through Cloudflare - CDN-added headers were absent;
  costs that only occur without them (such as WooCommerce's MaxMind lookup) may not
  apply to real visitors"
- "profiled through Cloudflare (visitor country header: XX)"
- "profiled through Cloudflare - no visitor country header; IP Geolocation is off in
  Cloudflare" (the toggle genuinely off case)

One re-run distinguishes the three states with data instead of inference.

## 0.9.14 (4th August 2026)

### Expandable phases

Dave's question "can these be expanded?" had a pleasing answer: the data was already in
every capture - `boot.hooks` (per-hook per-component ms), `boot.includes` (per-plugin
file load) and `boot.render.components` all ride the ajax payload - the popover just
never showed them. `phaseDetail()` maps each phase to its source (`plugin_includes` ->
includes; `plugins_loaded_callbacks` -> hooks.plugins_loaded; `init_callbacks` ->
hooks.init + hooks.widgets_init; `post_init_boot` -> hooks.wp_loaded +
hooks.rest_api_init; `theme_load_and_setup` -> hooks.after_setup_theme;
`render_and_output` -> render.components). Phase rows with detail get a caret and
pre-rendered hidden subrows (top 12 by ms); the difference between the wall-clock phase
and the timed detail is shown as "untimed / core framework" (or "theme templates +
direct output" for render). Core-before-plugins and routing have no per-component data
and render as plain rows. Because the sources were always captured, expansion works on
EXISTING stored results.

### Shrinking the untimed render remainder

Two new instruments, both feeding the render ledger:

- **WooCommerce layout hooks** join the wrapped list (before/after main content, shop
  loop + item hooks, single product summaries, sidebar). Anything `woocommerce_*` in
  the wrapped list is render-phase by prefix (`is_render_hook()`). No-ops without Woo.
- **Dynamic block timing**: `pre_render_block` (PHP_INT_MIN) pushes, `render_block`
  (PHP_INT_MAX) pops a LIFO stack; only blocks with a `render_callback` are tracked
  (static blocks are stored HTML), only OUTERMOST dynamic blocks are recorded (an inner
  block's time is inside its parent's - recording both would push the ledger past the
  segment), and attribution reflects the block's render_callback to the providing
  plugin's file.

Docker effect: home's render phase went from 32% timed (10 of 31.6ms) to 69% timed
(32.5 of 47.1ms). What remains untimed is genuinely the theme's own template code -
decomposing THAT needs function-level profiling (roadmap phases 5-6).

### Double-wrap fix (latent since 0.9.10)

`wrap_pending()` ran on EVERY firing of a hook. the_content and the Woo loop hooks fire
once per post/item, so each firing re-wrapped the already-wrapped callbacks - nested
timers recording the same work at every layer. On archive pages the render ledger could
overcount several-fold (masked by the untimed_ms >= 0 clamp). Now guarded once per
hook: the wrappers persist and time every subsequent firing; only the wrapping itself
happens once. Callbacks registered after a hook's first firing go untimed - acceptable
and documented.

## 0.9.7 (3rd August 2026)

### Bootstrap decomposition - the PHP-floor instrument

Driven by the live investigation: run 4 showed every anonymous page on
superspeedyplugins.com paying a ~500ms PHP floor (including the 404 - so bootstrap, not
content), and deep run 5's 66-plugin sweep could not decompose it: no single exclusion
moved any front-end page more than ~80ms, because the floor is 66 plugins each costing
slices below the noise gate. Single-out exclusion is structurally blind to
death-by-a-thousand-cuts. The alternatives (excimer/xhprof) need PECL installs most
customers cannot do.

New `profiler/class-sspa-boot-timer.php` (standalone, armed-request-only), installed by
`SSPA_Capture::arm()` - which runs from the mu-loader, before any regular plugin loads,
the only vantage point from which per-plugin include timing is possible:

- **Per-plugin include timing**: core fires `plugin_loaded` after each plugin file;
  deltas between events = that plugin's include + top-level cost. First plugin absorbs
  core's small l10n setup (approximate, documented).
- **Milestone ledger**: `muplugins_loaded`, `plugins_loaded` (PHP_INT_MIN/MAX), `init`
  (MIN/MAX), `after_setup_theme`, `wp_loaded`, `template_redirect` - derived into named
  phases (core boot, plugin includes, plugins_loaded callbacks, theme setup, init,
  routing/query).
- **Per-callback hook timing**: for each profiled hook (`plugins_loaded`,
  `after_setup_theme`, `init`, `widgets_init`, `wp_loaded`, `wp_enqueue_scripts`,
  `admin_init`, `admin_menu`, `admin_enqueue_scripts`, `template_redirect`,
  `rest_api_init`), a PHP_INT_MIN callback wraps every later-priority callback in a
  timing closure AS THE HOOK STARTS. WP_Hook reads each priority bucket live, so
  mutating buckets it has not reached is safe, and wrapping from inside the hook catches
  callbacks regardless of when they were registered (the failure mode of wrap-early
  approaches: WooCommerce registers most of its init work during plugins_loaded).
  Each callback is attributed via reflection + the component map at report time.

Capture gains a `boot` section (`segments`, `includes`, `hooks`, `components` - the
combined per-plugin ranking of include + callback ms - and `top_callbacks`); stored in
the existing profile blob, no schema change. `ajax_page_detail` passes it through and
the Pages drill-down renders three tables: request phases, PHP cost per plugin, slowest
callbacks.

Verified in docker (05-run-e2e, new assertions): WooCommerce include timed and
attributed, init callbacks timed, page renders identically with every callback wrapped.

Overlap caveat, stated in the class docblock: a plugin's include time and its hook
callback time are separate rows of one story; hook totals must not be blindly summed
with segment totals.

plugin-editor loopback sandbox tests, and its only reader in core), so profiled-request
fatals neither email nor trip recovery mode. Real traffic never reaches the mu-loader's
token path, so its protection is unchanged.

### Fatal cells surfaced as discovered dependencies

`sweep_deltas()` marks an unresolved cell `fatal` when it 5xx'd with a healthy baseline;
`finish_sweep()` collects them into the run notes as `fatal_cells` and the Overview's
deep panel renders them: plugin + page, with the explanation that this is a hard runtime
dependency discovered by experiment, that only the analysis's own requests saw the
error, and that any WordPress "technical issue" email during the run was this - usually
blaming the plugin whose file threw rather than the excluded one.


### Resolve permastruct placeholders in CPT archive URLs

Found by run 4 on live (the first 0.9.4 run): its single unmeasured page was
`cpt-kb-archive`, catalogued at the literal URL `/kb/%kb_category%/`.
`get_post_type_archive_link()` returns the permastruct TEMPLATE, placeholder and all, for
a CPT whose rewrite embeds a taxonomy. The request runs PHP (600ms walls observed), but
the `%` signs are re-encoded in transit, so `REQUEST_URI` no longer matches the token's
signed path - the mu-loader stays inert, no canary, every sample wasted as `no_canary`.

Fix in `SSPA_Catalogue`: `resolve_permastruct_tokens()` substitutes each `%token%` whose
name is a real taxonomy with that taxonomy's biggest term (by count, hide_empty), and
returns null - page skipped - when a placeholder cannot be resolved. Note for a KB-style
CPT the resolved archive URL coincides with the `tax-kb_category` page; the duplicate
measurement is accepted rather than special-cased.

All four changes fall out of one comparison: two baseline runs on live
superspeedyplugins.com, run 1 with Query Monitor active (riding its db.php), run 2 with QM
deactivated but - unknown at the time - its db.php drop-in still in place. The two runs
disagreed everywhere, and each disagreement was a bug.

### Cache-busting profiling requests

**Symptom:** home, shop, product-single and every other pretty-URL anonymous page had NULL
metrics in both runs, with samples recording `error: no_canary` and wall times of 11-24ms -
a full-page cache answering. The only pages that profiled were the ones a cache never
serves: query-string URLs (`?s=`, the probes, the randomised 404 URL) and the
cache-excluded WooCommerce endpoints. The run then completed "done" and scored the site
off the unrepresentative remainder.

**Cause:** the profiling token travels in the `X-SSPA-Token` request header, and the
crawler sent `Cache-Control: no-cache` as a request header. Page caches key on the URL and
vary on neither, so nginx fastcgi_cache served the stored HTML and PHP (and the
mu-loader canary) never ran.

**Fix** (`includes/class-sspa-crawler.php`):

- Every signed request now appends `sspa_nc=<12 hex chars>` via `bust_url()` - a unique
  URL per request guarantees a cache MISS on anything that keys on the URL. The token
  signature already binds to path+query (`SSPA_Token::request_path()`), so the arg is
  minted into the signature and cannot be stripped or replayed onto another URL. Redirect
  hops re-bust (add_query_arg replaces the previous value); the signed warm-up used by
  isolation/cache-off jobs busts too. The unsigned warm-up deliberately does not - warming
  the cache is its job.
- `looks_cached()` now also recognises `x-fastcgi-cache`, `x-vercel-cache`, `x-qc-cache`
  and a non-zero `Age` response header.

`mu/sspa-loader.php` additionally sends `Cache-Control: no-store, no-cache,
must-revalidate, max-age=0` on every token-verified response: a profiled response stored
by a cache would be served to real visitors and would answer later profiling requests
without running PHP. (Template change - reinstalled automatically by `ensure_installed()`
on the next admin page load because the generated content differs.)

### Attribution: skip the db layer

**Symptom:** 100% of queries in BOTH runs attributed to `query-monitor` (17,586 and
18,378 queries respectively); every other component at zero. Findings evidence showed
`"caller":"QM_DB->query (DB.php:0)"` - including in run 2 where QM was not an active
plugin.

**Cause:** when parsing QM-format `$wpdb->queries`, `attribute_from_summary()`
(`profiler/class-sspa-component-map.php`) resolves callable names to files by reflection.
`QM_DB->query` is the innermost resolvable frame of every stack, it resolves into
`plugins/query-monitor/`, and `chain()` had no concept of "the db layer is transport, not
spender" - it skips core and our own frames only.

**Fix:** `is_db_layer()` - a cached reflection check that skips any frame whose class is
`wpdb` or a subclass of it (QM_DB, LudicrousDB, anything else). Applied in
`attribute_from_summary()` before file resolution. The frames-based path (our own
profiling wpdb) never had the bug: our frames are own-dir and already skipped.

### Honest drop-in health + stale-QM handling

**Symptom 1:** run 1 (QM plugin active) captured full per-query data on logged-in admin
pages but NOTHING on anonymous pages - QM only collects when the viewer could see its
output. The Overview meanwhile claimed "riding Query Monitor's db.php - full detail
available", and the swap checkbox was only rendered for `foreign` drop-ins, never `qm`
(the backend honoured `swap_dropin` for both all along).

**Symptom 2:** deactivating QM left its db.php behind (an orphan that still executes
standalone), `ensure_installed()` correctly refuses to overwrite a foreign file, and
nothing anywhere said so.

**Fixes** (`class-sspa-helper-files.php`, `tabs/overview.php`, run controller AJAX):

- `qm_plugin_active()` / `dropin_is_stale_qm()` / `replace_stale_qm_dropin()` - the
  replace renames the orphan to `db.php.qm-stale-<timestamp>` (never deletes) and installs
  ours; QM reinstates its own copy if reactivated.
- Health surfaces `stale_qm` and `qm_active`. Overview: active QM gets a warning
  (anon capture missing, backtrace overhead) plus the swap checkbox; stale QM gets a red
  line and a one-click "Replace it with ours" button (`wp_ajax_sspa_replace_stale_dropin`).

### Unknown is not zero

**Symptom:** run 1's blind anonymous pages stored `sql_ms = 0`, `rows = 0`,
`dupe_query_count = 0` - indistinguishable from a page that genuinely spent no time in
SQL, and `php_ms` silently absorbed the entire generation time.

**Fix:** `collect_sql()` (`profiler/class-sspa-capture.php`) returns null for
`total_ms`/`rows_total`/`dupe_count` in `mode === 'none'` (the query count stays - it
comes from `$wpdb->num_queries` and is real). `SSPA_Profile_Store` only derives `php_ms`
when both gen and sql are known. `finish()` counts profiles with NULL `page_gen_ms` (and
no `blocked_by`, excluding baseline/mail-probe) into the run notes as `unmeasured_pages`;
the Overview shows a red incomplete-run notice and the Pages tab marks each such row
"not measured - cache served it".

The two live runs (wp_sspa_runs 1 and 2 on superspeedyplugins.com) are the reference
dataset for all four bugs; the misattribution is visible in `wp_sspa_component_stats`
(100% query-monitor) and the cache skips in `wp_sspa_profiles.samples` (`no_canary`,
